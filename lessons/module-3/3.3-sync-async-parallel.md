# 3.3 同步、异步与多路并行推理

> **对应 SLT**：我能实现同步、异步与多路异步三种推理模式。
> **课时类型**：Developer Documentation
> **语言**：C++（TensorRT + CUDA Runtime）
> **版本**：TensorRT 10.10.0.31（API 已核对）

---

## 版本说明（TensorRT 10.10）

本课基于 **TensorRT 10.10.0.31**。10.x 与 8.x 的 API 差异较大，先记住四条：

- **`enqueueV3(stream)` 是唯一的 enqueue API**，8.x 的 `enqueueV2` 已移除。
- **张量按名字绑定**：`setTensorAddress(name, ptr)`。8.x 的 binding index（`setBinding`）已移除。
- **`kEXPLICIT_BATCH` 已废弃**。TensorRT 10 的网络**永远是 explicit batch**，`createNetworkV2(0)` 即可，不要再传该 flag。
- **engine 与 TensorRT 版本强绑定**。10.10 构建出的 `.engine` 不能在其它 TRT 版本直接加载，除非启用 version-compatible 模式。这正是部署时要缓存/重建 engine 的原因。

> 官方对 `enqueueV3` 的警告值得先记住：**不要用默认 stream**，否则 TensorRT 会插入额外的 `cudaDeviceSynchronize()`，把异步又变回同步。这正好是本节要解决的问题。

---

## 一次推理的时间都花在哪了

把一次推理拆开看，端到端时间由三段构成：

1. **上传（H2D）**：把预处理好的输入从主机内存送到显存。
2. **计算**：TensorRT 在 GPU 上执行网络。
3. **回传（D2H）**：把输出张量从显存拷回主机内存。

三段里只有第二段真正占用算力。上传和回传期间，GPU 的计算单元在等数据；计算期间，CPU 在等 GPU。同步推理把三段首尾相接，于是 CPU 与 GPU 交替空转，两端都没跑满。

异步推理要解决的就是这件事：**让上传、计算、回传重叠起来**，把空闲时间填上。

```text
同步（串行）：  [上传][计算][回传]  [上传][计算][回传]
异步（流水）：  [上传][计算][回传]
                    [上传][计算][回传]
                        [上传][计算][回传]
```

---

## CUDA Stream：异步的执行队列

异步的载体是 **CUDA stream**。可以把 stream 理解成一条有序操作队列：

- 你在同一个 stream 上排队的所有操作，**按提交顺序执行**。
- **不同 stream 之间可以并发**。
- 提交操作（`enqueueV3`、`cudaMemcpyAsync`）本身**立即返回**，不会阻塞 CPU。
- `cudaStreamSynchronize(stream)` 会阻塞 CPU，直到该 stream 上所有操作完成。

```cpp
cudaStream_t stream;
cudaStreamCreate(&stream);
```

TensorRT 的 `IExecutionContext::enqueueV3(stream)` 是 **stream-ordered** 的：它把推理任务排进 stream 后立刻返回，真正的执行由 GPU 异步完成。

> **关键认知**：异步 API ≠ 并行。用 `enqueueV3` 提交任务后 CPU 不再空等，但在**同一个 execution context** 上，你无法让两次推理同时在跑——context 每次只能承载一次推理。要真正并行，需要**多个 context**。

---

## 模式一：同步推理

最少的心智负担。提交、等待、读取，一气呵成。

```cpp
bool inferSync(nvinfer1::IExecutionContext* ctx, cudaStream_t stream,
               void* d_input, void* d_output, void* h_output, size_t out_bytes)
{
    if (!ctx->enqueueV3(stream)) return false;                    // 排入 stream
    cudaMemcpyAsync(h_output, d_output, out_bytes,
                    cudaMemcpyDeviceToHost, stream);              // 排入 stream
    cudaStreamSynchronize(stream);                                // 阻塞直到全部完成
    return true;
}
```

**特点**：逻辑线性、结果随时就绪、容易调试。代价是 CPU 全程陪跑。
**适用**：离线批处理、单目标实时、延迟远大于吞吐需求的场景。

---

## 模式二：单路异步推理

把「提交」和「取结果」拆开。提交后 CPU 立刻返回去做别的事——取下一帧、跑预处理、更新界面——直到真正需要结果时才同步。

```cpp
// 提交阶段：只入队，不等待
bool submit(nvinfer1::IExecutionContext* ctx, cudaStream_t stream,
            void* d_input, void* d_output, void* h_output, size_t out_bytes)
{
    if (!ctx->enqueueV3(stream)) return false;
    cudaMemcpyAsync(h_output, d_output, out_bytes,
                    cudaMemcpyDeviceToHost, stream);
    return true;   // 立即返回
}

// 消费阶段：需要结果时才等
void collect(cudaStream_t stream)
{
    cudaStreamSynchronize(stream);
    // 此时 h_output 已就绪
}
```

**特点**：隐藏了「提交到消费」之间的等待，CPU 利用率提升。
**瓶颈**：下一次提交前，必须保证上一次推理已经用完 context。于是很快退化成「一次只能有一帧在途」。

---

## 模式三：多路并行推理

让 GPU 始终有活干，就得让**多帧同时在途**。做法是创建 **N 个 execution context**，每个绑定自己的输入/输出缓冲区和 stream，然后轮转提交。

多个 context 由**同一个 engine** 创建，它们**共享网络权重**，因此显存开销主要来自各自的输入输出缓冲区，而不是 N 份模型。

```cpp
const int N = 3;   // 并行路数

std::vector<nvinfer1::IExecutionContext*> ctxs(N);
std::vector<cudaStream_t> streams(N);
std::vector<void*> d_in(N), d_out(N), h_out(N);

for (int i = 0; i < N; ++i) {
    ctxs[i] = engine->createExecutionContext();        // 独立 context
    cudaStreamCreate(&streams[i]);                     // 独立 stream
    cudaMalloc(&d_in[i],  input_bytes);
    cudaMalloc(&d_out[i], output_bytes);
    cudaMallocHost(&h_out[i], output_bytes);           // 页锁定内存，异步传输才有效
    ctxs[i]->setTensorAddress("images",  d_in[i]);
    ctxs[i]->setTensorAddress("output0", d_out[i]);
}

// 轮转提交：第 k 帧交给第 k % N 路
void submitFrame(int k, const void* h_input)
{
    int i = k % N;
    cudaMemcpyAsync(d_in[i], h_input, input_bytes,
                    cudaMemcpyHostToDevice, streams[i]);
    ctxs[i]->enqueueV3(streams[i]);
    cudaMemcpyAsync(h_out[i], d_out[i], output_bytes,
                    cudaMemcpyDeviceToHost, streams[i]);
}

// 按提交顺序回收，保证帧与结果对齐
void collectFrame(int k)
{
    int i = k % N;
    cudaStreamSynchronize(streams[i]);
    // h_out[i] 是第 k 帧的结果
}
```

**特点**：GPU 被喂饱，吞吐显著上升。
**代价**：单帧延迟可能升高（排队），显存占用 N 倍缓冲，代码复杂度上升。

---

## 实现要点（踩坑清单）

**每个 context 必须有独立缓冲区。** 两个 stream 同时读写同一块显存就是数据竞争，结果会随机错乱。这是多路并行最容易踩的坑。

**缓冲区要用页锁定内存。** `cudaMallocHost` 分配的页锁定（pinned）内存才能让 `cudaMemcpyAsync` 真正异步；用普通 `new`/`malloc` 的内存，驱动会退化成同步拷贝，异步就白做了。

**提交顺序与回收顺序必须一致。** 轮转提交就必须轮转回收。否则你拿到的是别的帧的结果，模型没坏，数据对错了。

**同步尽量用事件而非整条 stream。** `cudaEventRecord` + `cudaEventSynchronize` 可以只等待某个时间点，减少整条 stream 全等的空耗。

**动态 shape 要在提交前设置。** 使用 shape tensor 或 `setInputShape` 时，每次形状变化都要在 `enqueueV3` 之前设置好，否则会用到上一次的形状。

**不要跨 stream 复用未同步的缓冲区。** 一块缓冲区在被 stream A 用完之前，不能被 stream B 写入。

> **进阶**：把「上传 → 推理 → 回传」的重复 launch 序列用 CUDA Graph 捕获成一张图，可以进一步降低 CPU launch 开销。这是延迟优化的下一步，先掌握多路并行再考虑。

## 动手验证

编译一个包含上面三种模式的小程序，对**同一张输入**跑 300 次，观察吞吐与延迟。

1. **同步模式**：跑 300 次，记录总耗时与 FPS。
2. **单路异步**：同样 300 次，记录 FPS 变化。
3. **多路并行（N=3）**：轮转提交 300 帧，记录 FPS。
4. **破坏性实验**：把 N 路改成共用同一块 `d_in`，再跑一次，观察输出是否出现错帧。

**验证要点**：程序必须打印出每次实验的 `平均耗时` 与 `FPS`，而不是静默跑完。没有可见输出，你无法判断异步是否真的生效。

**预期方向**：
- 多路并行的 **FPS 应高于** 单路异步（GPU 被喂饱）。
- 多路并行的**单帧延迟通常不低于**同步模式（排队成本）。
- 破坏缓冲区隔离后，会出现**肉眼可见的结果错乱**——这正是数据竞争的实证。

---

## 常见错误

| 现象 | 原因 | 处理 |
|---|---|---|
| 异步后 FPS 没变化 | 用了普通内存做传输 | 改用 `cudaMallocHost` 页锁定内存 |
| 结果偶发错帧 | 多路共用缓冲区 | 每路独立 buffer |
| 程序崩溃或结果全错 | 同一 context 被并发重入 | 一个 context 一次只跑一次推理，并行靠多 context |
| 结果少一帧或错位 | 提交与回收顺序不一致 | 用同一个索引轮转 |
| `enqueueV3` 返回 false | shape 未设置或 buffer 未绑定 | 提交前检查 `setInputShape` / `setTensorAddress` |
