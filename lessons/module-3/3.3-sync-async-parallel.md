# 3.3 同步、异步与多路并行推理

> **对应 SLT**：我能实现同步、异步与多路异步三种推理模式。
> **课时类型**：Developer Documentation
> **语言 / 版本**：C++17，TensorRT 10.10.0.31，CUDA Runtime
> **前置**：[3.2 分配缓冲区，在 CUDA 流上执行推理](3.2-buffers-and-stream.md)
> **完整代码**：[`3.3-infer-modes.cpp`](../../assets/code-examples/3.3-infer-modes.cpp)

本节沿用 3.2 的按名字绑定方式：`setTensorAddress` 绑定地址，`enqueueV3(stream)` 提交推理。三种模式使用同一个 Engine，差别在于**何时等待结果、允许几帧在途、什么时候复用资源**。这里的“同步推理”是应用接口同步返回，内部仍可使用异步 CUDA API。

配套程序只处理**静态形状、一个普通数据输入和一个输出、FP32 / LINEAR / DEVICE、非形状推导 I/O**。名字与尺寸从 Engine / Context 查询，不写死 `images` 或 `output0`。动态形状、多 I/O、数据依赖输出的扩展见后文；不要只修改几个维度就认为示例已经支持这些模型。

## 1. 先区分“CPU 返回”和“GPU 完成”

一次请求包含四步：CPU 准备输入 → H2D 上传 → GPU 推理 → D2H 回传。CPU 读取输出之前，还必须确认 D2H 已完成。

| 模式 | 应用何时返回 / 等待 | 本例最大在途 GPU 请求 | 可能重叠的工作 |
|---|---|---:|---|
| 同步 | 提交后立即等待并取走结果 | 1 | 本例不主动安排跨请求重叠 |
| 单路异步 | 提交与回收分开，需要结果时再等 | 1 | 本帧 GPU 工作与下一帧 CPU 准备 |
| N 路并行 | 多个独立槽位提交，满了再等待空位 | N | 不同帧的传输 / 计算，以及 CPU 工作 |

本节将一个独立执行单元称为 **slot（槽位）**：它拥有 Context、stream、输入输出缓冲区、完成事件和当前帧编号。这里的“路数”指槽位数，不要求恰好等于摄像头数量。

```text
时间向右 →

同步：
CPU      准备 A | 提交 A | 等待........ | 取 A | 准备 B | ...
stream0                 H2D A → 推理 A → D2H A

单路异步：
CPU      准备 A | 提交 A | 准备 B........ | 等待/取 A | 提交 B
stream0                 H2D A → 推理 A → D2H A

多路：
stream0     H2D A → 推理 A → D2H A                H2D D → ...
stream1          H2D B → 推理 B → D2H B
stream2               H2D C → 推理 C → D2H C
```

最后一幅只是**允许重叠的示意**，不是承诺 GPU 按这个时间线执行。必须记住：

- 同一 stream 内的工作按序执行，`H2D → 推理 → D2H` 不需要在每一步之间加 CPU 同步。
- 不同 stream 提供并发机会；是否实际重叠取决于 GPU 的复制引擎、计算资源、模型和调度。
- `Async` / `enqueue` 表示提交接口，不能保证调用始终立即返回。普通主机内存暂存、内部资源分配、某些网络特性、插件或 weight streaming 都可能引入等待。
- 本例限制每个 Context 同时只服务一个尚未回收的请求，便于管理资源。这不是说固定配置的同一 stream 永远不能连续排队多次推理；连续排队仍是有序执行，还要单独解决输入、输出与状态的生命周期。

CUDA 的主机返回语义见 [API Synchronization Behavior](https://docs.nvidia.com/cuda/archive/11.8.0/cuda-runtime-api/api-sync-behavior.html)；TensorRT 的执行、内存与默认 stream 约束见 [10.10 Runtime 头文件](https://github.com/NVIDIA/TensorRT/blob/release/10.10/include/NvInferRuntime.h)。

## 2. 公共实现：先把一个槽位做对

### 2.1 每个槽位拥有哪些资源

```text
一个共享 Engine
    ├── slot 0：context 0 + stream 0 + done 0 + h_in/h_out + d_in/d_out
    ├── slot 1：context 1 + stream 1 + done 1 + h_in/h_out + d_in/d_out
    └── slot 2：context 2 + stream 2 + done 2 + h_in/h_out + d_in/d_out
```

并发运行的槽位拥有独立的可写缓冲区和 Context；共享 Engine 允许共享权重。除了应用 I/O，每个 Context 还会消耗执行状态、activation / scratch 等内部内存，因此不能只用 `N × 输入输出字节数` 估计总显存。

完整程序先遍历 `getNbIOTensors()`，检查数量、方向、数据类型、格式、位置和 `isShapeInferenceIO()`，再计算容量。必须拒绝未解析维度与乘法溢出，具体检查方法沿用 3.2。

下面是核心初始化顺序；错误检查、类定义和异常清理由配套 `.cpp` 给出：

```cpp
// input_name / output_name、in_bytes / out_bytes 已由模型查询和校验得到。
context.reset(engine.createExecutionContext());
if (!context) throw std::runtime_error("创建 Context 失败");

CUDA_CHECK(cudaStreamCreateWithFlags(&stream, cudaStreamNonBlocking));
CUDA_CHECK(cudaEventCreateWithFlags(&done, cudaEventDisableTiming));
CUDA_CHECK(cudaMallocHost(&h_in, in_bytes));
CUDA_CHECK(cudaMallocHost(&h_out, out_bytes));
CUDA_CHECK(cudaMalloc(&d_in, in_bytes));
CUDA_CHECK(cudaMalloc(&d_out, out_bytes));

if (!context->setTensorAddress(input_name, d_in) ||
    !context->setTensorAddress(output_name, d_out))
    throw std::runtime_error("绑定张量地址失败");
```

`cudaStreamNonBlocking` 控制该 stream 与 legacy 默认 stream 的隐式同步关系，不代表等待函数不再阻塞 CPU。TensorRT 10.10 建议使用非默认 stream，避免默认 stream 可能触发的额外设备同步。

`done` 只用于判断完成，不用于计时，因此禁用 timing。性能分析需要另外创建启用 timing 的事件；不能拿这里的 `done` 调用 `cudaEventElapsedTime`。

等待方式也有 CPU 开销：这里的 `cudaEventSynchronize` 可能让主机线程忙等。若更关心 CPU 占用，可在创建完成事件时组合 `cudaEventDisableTiming | cudaEventBlockingSync`，让等待线程睡眠；唤醒延迟与吞吐要在目标环境实测。相关语义见 [CUDA 事件 API](https://docs.nvidia.com/cuda/archive/11.8.0/cuda-runtime-api/group__CUDART__EVENT.html)。

**分配放在初始化阶段。** 在逐帧路径中反复 `cudaMalloc`、`cudaMallocHost`、创建 Context 或销毁资源，会增加开销，并可能破坏并发。页锁定内存也不宜无限增长，应按有界槽位池预分配。

### 2.2 `submit`：复制到本槽位，再按序提交

配套类的接口是：

```cpp
void submit(uint64_t id, const std::vector<float>& input);
bool ready() const;
void collect(uint64_t expected_id, std::vector<float>& output);
bool busy() const;
uint64_t frameId() const;
```

`submit` 的关键步骤如下，省略了成员限定和错误信息拼接：

```cpp
if (busy) throw std::runtime_error("槽位仍在使用，先 collect");
if (input.size() != input_elements)
    throw std::runtime_error("输入元素数不匹配");

// input 可以是普通 vector：CPU 同步复制到本槽位拥有的 pinned 缓冲。
std::memcpy(h_in, input.data(), in_bytes);
frame_id = id;
busy = true; // 后续提交若失败，也不能当作空闲槽位继续使用。
CUDA_CHECK(cudaMemcpyAsync(d_in, h_in, in_bytes,
                          cudaMemcpyHostToDevice, stream));
if (!context->enqueueV3(stream))
    throw std::runtime_error("enqueueV3 失败");
CUDA_CHECK(cudaMemcpyAsync(h_out, d_out, out_bytes,
                          cudaMemcpyDeviceToHost, stream));
CUDA_CHECK(cudaEventRecord(done, stream)); // 必须放在 D2H 后面。
```

这里的两次复制承担不同职责：CPU `memcpy` 把调用方数据交给槽位所有；H2D 把 pinned 数据上传到设备。`submit` 成功返回后，调用方可以复用自己的普通 `input`，但不能覆盖槽位的 `h_in`。真正预处理时，也可以直接写空闲槽位的 pinned 输入，省掉一次 CPU 复制；此时写入方必须遵守槽位所有权。

异步 CPU↔GPU 传输使用页锁定主机内存。若直接把普通 `vector.data()` 传给 `cudaMemcpyAsync`，可能发生暂存或主机同步，不能据此假定有稳定的异步行为与重叠收益。页锁定是实现重叠的重要条件，也不能单独保证加速。

成功入队不代表完成。若提交中途某一步失败，前面已提交的工作可能仍在执行；完整程序抛出异常并退出当前运行，由 RAII 等待 stream 后清理。**不能仅把 `busy` 改回 false 就继续复用。** 本例不提供失败后继续 `ready/collect` 的恢复协议。

### 2.3 `ready`：只查询，不读取未完成结果

```cpp
if (!busy) return false;
const cudaError_t status = cudaEventQuery(done);
if (status == cudaSuccess) return true;
if (status == cudaErrorNotReady) return false;
CUDA_CHECK(status); // 其他错误必须报告，不能一概当成“还没好”。
return false;
```

必须先检查 `busy`，避免把尚未关联请求的事件误当成完成结果。`ready()` 返回 true 只说明该事件覆盖的 GPU 工作完成；CPU 还没有把输出消费走，槽位仍然不能复用。

不要在主线程写无休止的 `while (!ready()) {}`。这会占满一个 CPU 核；可以处理独立工作、使用有等待策略的调度，或直接进入 `collect` 阻塞等待。

### 2.4 `collect`：确认身份，等待，取走输出，释放槽位

```cpp
if (!busy || frame_id != expected_id)
    throw std::runtime_error("请求编号不匹配，或已重复回收");

CUDA_CHECK(cudaEventSynchronize(done));
output.resize(output_elements);
std::memcpy(output.data(), h_out, out_bytes);
busy = false; // 在结果拥有自己的内存后才释放槽位。
```

结果保存在调用方的 `vector` 中，拥有独立存储。若返回裸 `h_out` 指针，槽位一复用，旧结果就可能被覆盖；除非另有明确的借用与释放协议，否则不要这样做。

完整生命周期是：

```text
空闲 → CPU 写输入 / 提交 → 在途 → done 完成 → CPU 取走结果 → 空闲
                                         ↑
                              GPU 完成不等于已消费
```

本例只在主线程调度，帧编号在一次运行中不重复，`busy + frame_id` 足以检查内部回收。将接口提供给多个生产者、长期运行服务或外部调用方时，应增加 `slot + generation + frame_id` token，拒绝陈旧 token、重复回收和错误槽位，见 [5.3](../module-5/5.3-capstone-project.md)。

## 3. 模式一：同步推理，先建立正确基线

只创建一个槽位，每次提交后立即回收：

```cpp
Slot slot(engine, io); // io 是经检查的 IOInfo，定义见完整程序。
std::vector<float> input(io.in_elements), output;
for (uint64_t id = 0; id < frames; ++id) {
    prepareInput(id, input);
    slot.submit(id, input);
    slot.collect(id, output); // 等 D2H 完成，复制结果，再处理下一帧。
    // 使用 output；需要保留时另行保存。
}
```

这里复用同一组资源完全安全，因为下一次写输入之前，上一次已消费完成。用 `cudaStreamSynchronize` 也能实现同步基线；本节统一使用 D2H 后的事件，便于三种模式共用回收代码。

同步适合调试、建立数值参考，以及下一帧必须依赖本帧结果的闭环任务。它不是“CPU 永远没有其他工作可做”的结论，而是当前调用线程在这个接口处等待结果。

不要为了实现同步在 H2D、推理、D2H 后分别调用 `cudaDeviceSynchronize()`。同 stream 的顺序已保证依赖；最后等待一次即可，设备级等待还会影响其他 stream。

## 4. 模式二：单路异步，让 CPU 与 GPU 各做自己的工作

单路异步保留一个槽位，将提交与回收之间的时间交给独立 CPU 工作。常见例子是准备下一帧，但前提是下一帧不依赖当前输出。

```cpp
std::vector<float> current(io.in_elements), next(io.in_elements), output;
prepareInput(0, current); // frames 已检查为正数。
for (uint64_t id = 0; id < frames; ++id) {
    slot.submit(id, current);

    if (id + 1 < frames)
        prepareInput(id + 1, next); // 只写 next，不碰 slot 的 pinned 输入。

    // 可在这里调用 ready() 决定是否继续处理独立工作。
    slot.collect(id, output);      // 还未完成就等待；已完成则直接取走。
    current.swap(next);
}
```

为什么需要 `current` / `next` 两个 CPU 容器？为了清楚表达上一帧的提交数据与下一帧的准备数据。由于 `submit` 已先复制到槽位，实际上也可以复用调用方的普通容器；但绝不能让下一帧预处理直接覆盖正在 H2D 的 `h_in`。

在理想条件下，忽略小额提交开销，稳态每帧周期可能从 `T_CPU准备 + T_GPU链路` 接近 `max(T_CPU准备, T_GPU链路)`。这是 CPU 与 GPU 的重叠，不是同一 stream 上 H2D、推理和 D2H 自己变成并行。

**没有独立 CPU 工作时，单路异步很可能与同步一样快。** 如果 `submit` 后马上 `collect`，两者执行路径本来就几乎相同；如果必须靠当前检测结果生成下一输入，也不能随意使用上述预取方式。

另一个边界是 CPU 后处理：回传结果必须完成后才能读取；若下一帧先提交，再在 CPU 上处理上一帧，可以让两者重叠，但要先把上一帧输出复制到独立结果对象，并处理好业务依赖。

## 5. 模式三：多槽位并行，关键是复用前回收

为每个槽位创建独立 Context、stream 和缓冲区，多个槽位共享一个 Engine。**一个 CPU 线程就可以向 N 条 stream 提交工作**，不必先引入 N 个 CPU 线程。

### 5.1 有界环形调度：先填充，再轮转，最后排空

```cpp
std::vector<std::unique_ptr<Slot>> slots;
for (size_t i = 0; i < lanes; ++i)
    slots.push_back(std::make_unique<Slot>(engine, io));

std::vector<float> input(io.in_elements), output;
uint64_t next_collect = 0;
for (uint64_t id = 0; id < frames; ++id) {
    // 每帧计时应在等待空槽位之前开始，包含背压。
    Slot& slot = *slots[id % lanes];
    if (slot.busy()) {
        // 此槽位中仍是 id-lanes 的旧帧，先取走，不能直接覆盖。
        slot.collect(next_collect, output);
        // 在这里消费 next_collect 对应的 output。
        ++next_collect;
    }
    prepareInput(id, input);
    slot.submit(id, input);
}

// 提交结束不等于全部完成。按编号回收所有尾请求。
while (next_collect < frames) {
    slots[next_collect % lanes]->collect(next_collect, output);
    // 在这里消费 next_collect 对应的 output。
    ++next_collect;
}
```

`lanes`、`frames` 必须是正数；示例命令行会检查。完整程序在复用槽位时从 `frameId()` 获取旧请求编号，结尾从最早未消费的帧开始排空，与上面的 `next_collect` 写法等价。

以 `lanes=3、frames=8` 为例：

| 即将提交的帧 | 使用槽位 | 提交前必须做什么 |
|---:|---:|---|
| 0、1、2 | 0、1、2 | 初次填充，无旧结果 |
| 3 | 0 | 回收帧 0，再提交帧 3 |
| 4、5 | 1、2 | 分别回收帧 1、2 |
| 6、7 | 0、1 | 分别回收帧 3、4 |
| 提交完毕 | 2、0、1 | 排空帧 5、6、7 |

最后一行说明为什么不能在结尾简单按槽位 `0..N-1` 输出结果：帧序可能跨过环形边界。按请求编号找到正确槽位，并核对 `frame_id`，就能处理帧数小于路数、非整除路数和多次绕环。

### 5.2 背压、保序与按完成顺序回收

槽位满时等待最早请求，使在途数量始终不超过 N，这就是**背压**。没有背压而不断往队列追加，会让排队延迟和内存持续增长；看起来提交很快，结果却越来越旧。

上述代码选择**按提交顺序消费**，结果天然保序。代价是帧 0 很慢、帧 1 已完成时，帧 1 也可能被挡住，这叫队头阻塞。

也可以查询所有在途槽位，优先消费已完成者，但必须按 `frame_id` 把结果交给正确输入。业务需要顺序时，再放入有界重排队列；业务接受乱序时，可直接返回对应请求。**回收顺序一致是本例的策略，不是 CUDA 或 TensorRT 的硬性要求。**

### 5.3 多路与 batch、辅助 stream 的区别

| 手段 | 改变了什么 | 主要约束 |
|---|---|---|
| 增加 slots / Context | 多个独立请求同时在途 | 每路资源、共享 GPU 竞争、队列延迟 |
| 增大 batch | 一次推理装入多份样本 | Engine 支持的 shape/profile、组批等待 |
| TensorRT auxiliary streams | 单次推理内部某些层可在辅助流执行 | Engine 构建配置、网络结构、内部同步与内存 |
| 增加 CPU 线程 | CPU 准备、提交或消费并发 | 线程安全、资源所有权、CPU 竞争 |

这些手段可以组合，但应一次只改变一个变量测量。自定义插件若有全局可写状态，也要检查并发安全，不能仅靠增加 Context 就认为问题已经解决。

## 6. 资源、依赖和异常：实现时逐项核对

### 6.1 哪块内存什么时候才能复用

| 资源 | 最早可复用的条件 | 本例的保守做法 |
|---|---|---|
| 调用方普通 `input` | CPU `memcpy` 到槽位完成 | `submit` 成功返回后可改 |
| pinned `h_in` | H2D 已读完 | `collect` 后才改 |
| device `d_in` | TensorRT 已消费输入 | `collect` 后才改 |
| device `d_out` | 推理写完，且 D2H / 后续消费者已读完 | `collect` 后复用 |
| pinned `h_out` | D2H 已写完才可读，CPU 取走后才可覆盖 | 事件完成后复制到 `output` |
| Context / 内部执行内存 | 相关 GPU 执行完成，且无主机并发访问 | 槽位在途时不改形状或地址 |

进阶可以在 H2D 后记录独立事件，更早复用主机输入；也可用 TensorRT 的 `setInputConsumedEvent` 判断设备输入何时可复用。但它们都**不表示输出已回传完成**。先用一个 D2H 后事件保证正确，再按性能证据细分生命周期。

本例析构顺序是：**先等待本槽位 stream → 释放缓冲和事件 / stream → 销毁 Context → 销毁 Engine → 销毁 Runtime**，Logger 覆盖这些对象的生命周期。完整程序将 Context 成员声明在 CUDA 资源成员之前，利用成员逆序析构，使构造中途抛异常时也先等待 GPU。

析构是异常路径的尽力清理，不抛异常；正常回收必须检查等待的返回值，不能依赖析构发现错误。遇到非法访问等异步执行错误时，停止当前运行并定位原因，不在已损坏的执行状态上盲目继续。

### 6.2 跨 stream 连接必须显式表达依赖

若 GPU 预处理与 TensorRT 在同一 stream，按顺序提交即可。若预处理在 `pre_stream`、推理在 `infer_stream`，要在生产方记录事件、消费方等待：

```cpp
// ready_event 已创建；GPU 预处理写入该槽位的 d_in。
launchPreprocess(pre_stream, d_in); // 代表应用自己的 kernel 调用。
CUDA_CHECK(cudaEventRecord(ready_event, pre_stream));
CUDA_CHECK(cudaStreamWaitEvent(infer_stream, ready_event, 0));
if (!context->enqueueV3(infer_stream))
    throw std::runtime_error("enqueueV3 失败");
```

`cudaStreamWaitEvent` 在 GPU 队列上建立依赖，通常无需阻塞 CPU。事件应按槽位管理，不要在消费者建立正确依赖之前随意重录。后续还要保护预处理源图、`d_in` 和输出的生命周期；一条等待只解决这一处生产与消费关系。

**传输与计算重叠并不总要多个 Context。** 也可用双缓冲、复制 stream、推理 stream 和事件，让下一帧 H2D 与当前推理重叠，所有推理仍在一个 Context 的同一执行队列中串行。它的缓冲区与地址切换管理更复杂；本节选择独立 Context 槽位，先把请求并发模型讲清楚。

### 6.3 线程安全与设备选择

本例所有 CUDA 调用、Context 配置与提交都在同一 CPU 线程，使用当前默认设备。扩展多 GPU 时，在创建、使用和清理对应资源前选择正确设备。

扩展多线程时，给槽位明确的唯一所有者，或对完整的状态转换加锁。仅给 `enqueueV3` 外套一个锁，无法保护其他线程同时修改输入、形状、地址或回收结果。不要从多个线程 / stream 同时重入同一个 Context。共享日志器及自定义插件的可变状态也需要满足并发使用要求。

## 7. 动态形状和复杂模型怎么扩展

配套程序遇到动态形状会明确拒绝；不是用 `1` 替换 `-1`。扩展时按槽位执行以下顺序：

1. 等待该槽位旧请求完成，并消费结果。
2. 在该槽位 stream 上调用 `setOptimizationProfileAsync(profile, stream)`，再设置每个动态输入的 `setInputShape`。
3. 补齐形状推导所需的输入，调用 `inferShapes`，检查返回值，再从 **Context** 查询当前输出形状。
4. 检查各 I/O 的类型、格式、位置和容量。需要增长时安全地重新分配并绑定地址；若预先按上界分配，也要核对当前容量。
5. 提交 H2D、推理、D2H 和完成事件，记录本请求的实际形状与输出元素数。

选择 profile 的 stream 与推理 stream 不同时，应用必须建立同步关系。切换 profile 后也要重新设置动态输入形状，不能依赖前一帧状态。

**profile 共享要按版本判断。** TensorRT 10.10 的 `kPROFILE_SHARING_0806` 已废弃，头文件说明 profile sharing 从 10.0 起默认启用，不需要再打开此开关；不要套用旧版本“一条并发 Context 必须配一个重复 profile”的规则。每个 Context 仍保留独立的当前 shape、绑定和执行资源。10.10 的 `IExecutionContext` 总注释还残留独立 profile 的旧表述，核对时应同时查看 [PreviewFeature 的版本说明](https://github.com/NVIDIA/TensorRT/blob/release/10.10/include/NvInfer.h#L8664-L8669) 和实际使用版本，跨版本部署重新验证。

其他扩展各有独立工作：

- **多输入、多输出**：每个张量建立描述、容量、地址和复制方向，不能在遍历时只留下最后一个名字。
- **FP16 / 向量化 I/O / HOST I/O**：按真实类型、布局填充和位置处理，不能沿用 `float` 与“维度乘积 × 4”。Engine 内部 FP16 不表示 I/O 必为 FP16。
- **数据依赖输出**：即使输入形状固定，输出仍可能在执行前未知，需要 `IOutputAllocator` 或经验证的容量上界策略，不能 enqueue 后才补上输出空间。
- **CUDA Graph**：先证明 CPU launch 开销是瓶颈，再考虑捕获。每个槽位单独管理图与地址；形状 / 地址改变后不能直接沿用旧图，捕获前还要处理形状更新和首次执行等条件。

## 8. 编译完整示例并验证

### 8.1 编译与运行

在仓库根目录运行。以下是课程机器的安装路径，换机器时替换；不需要 OpenCV 或 ONNX Parser，只链接 `nvinfer` 和 `cudart`：

```bash
export TRT_ROOT="$HOME/tensorrt/TensorRT-10.10.0.31"
export CUDA_ROOT="$HOME/cuda-11.8"
export LD_LIBRARY_PATH="$TRT_ROOT/lib:$CUDA_ROOT/lib64:${LD_LIBRARY_PATH:-}"

g++ -std=c++17 -O2 -Wall -Wextra \
    assets/code-examples/3.3-infer-modes.cpp -o /tmp/infer-modes \
    -I"$TRT_ROOT/include" -I"$CUDA_ROOT/include" \
    -L"$TRT_ROOT/lib" -L"$CUDA_ROOT/lib64" \
    -lnvinfer -lcudart

/tmp/infer-modes homework/tensorrt/model/model.engine 300 3
```

参数依次是 Engine 路径、测量帧数、parallel 路数；后两项默认 300、3。程序先为不同伪输入生成同步参考，然后为各模式创建槽位、逐槽位预热并排空，单独验证三种模式，再输出性能统计。

源程序会检查不同帧编号与参考输出，容差采用 `abs(actual-ref) <= 1e-4 + 1e-3*abs(ref)`，并拒绝 NaN / Inf。这是本课程样例的管线验证阈值，真实模型须事先确定自己的容差；不要因某种模式更快就放宽。

伪输入按帧编号在 7 种输入之间轮换，避免只重复同一张输入掩盖错帧。它们只能检查这组输入上的数值和调度一致性，不能证明模型精度，也不能保证模型对这些输入必然有不同输出。业务验证还需要一组真实且有差异的预处理张量。

### 8.2 正确性要覆盖环形边界

先小规模验证，再测 300 帧以上：

```bash
/tmp/infer-modes homework/tensorrt/model/model.engine 1 3
/tmp/infer-modes homework/tensorrt/model/model.engine 8 3
/tmp/infer-modes homework/tensorrt/model/model.engine 17 1
/tmp/infer-modes homework/tensorrt/model/model.engine 17 2
/tmp/infer-modes homework/tensorrt/model/model.engine 17 4
```

验收时检查：

- 每帧只消费一次，帧编号无遗漏、无重复，测量消费数等于传入帧数。
- 输出形状 / 元素数正确，逐元素对照同步参考；验证发生在性能测量之外。
- 帧数小于路数、非整除路数、槽位多次复用，都能完成并排空。
- 忙槽位再提交、错误帧编号、重复回收应被接口拒绝。可临时在驱动代码中加入错误调用观察异常，不必制造 GPU 内存竞争。

不要以“共用一个缓冲后必须肉眼可见错乱”作为验证条件。数据竞争可能被重复输入、偶然串行和调度时机掩盖；一次没错不代表安全。若教学中保留竞争实验，应隔离运行，并明确它调用了未定义行为。

### 8.3 FPS 与单帧延迟分别计算

配套程序使用 `std::chrono::steady_clock`，不把 enqueue 调用耗时当成推理耗时：

```text
latency_i = 第 i 帧输出已复制到独立 CPU 结果的时间 − 该帧开始准备的时间
FPS       = 完成并消费的帧数 / 从首帧开始准备到末帧消费完成的总秒数
```

每帧开始时间在等待槽位之前记录，因此延迟包含该帧的背压等待。总窗口包含填充与排空；资源创建、同步参考、正确性检查和预热不进入性能窗口。单路异步的下一帧计时从它实际开始准备时起算，不能等到正式提交才开始。

本样例的口径包含伪输入生成、CPU→pinned 复制、H2D、推理、D2H、结果复制与回收，不含真实图片读取、业务预处理、解码、NMS 或画框。因此这是**样例推理链路性能**，不是完整检测器的端到端性能。程序报告 FPS 与逐请求 mean / p50 / p95；更完整的 p99、CSV 与业务计时协议见 [5.2](../module-5/5.2-benchmark-pipeline.md)。

并行时多个请求的延迟区间相互重叠，**`1000 / 平均延迟毫秒` 一般不等于 FPS**。也不要把 `总耗时 / 帧数` 改名为平均请求延迟。分位数与 5.2 一样，使用排序后 `(N−1)*p` 位置的线性插值。

本例固定依次运行三种模式，便于学习；正式性能结论应多轮交错或随机顺序运行，控制其他负载、热状态与功耗。先确认正确，再比较；不要求 parallel 一定胜出。

### 8.4 用时间线确认重叠

有 NVIDIA 驱动和 Nsight Systems 时，可以查看提交线程、复制引擎与 kernel 时间线：

```bash
nsys profile --trace=cuda,nvtx,osrt --output=/tmp/infer-modes-trace \
    /tmp/infer-modes homework/tensorrt/model/model.engine 300 3
```

检查不同 stream 是否确实有 H2D / 推理 / D2H 重叠，是否有默认 stream、分配或设备同步打断队列。profile 有额外开销，用它解释瓶颈，正式数字另跑。

**本轮验证范围**：编译、接口与调度检查的实际结果记录在 [`module-3-verification.md`](../../assets/code-examples/module-3-verification.md)。有编译环境不代表能访问 GPU；未执行的真机正确性与性能项目会明确列出，不提供推测 FPS。

## 9. 怎么选择与调优

| 需求 / 现象 | 建议 | 为什么 |
|---|---|---|
| 首次接入、数值不对、单帧闭环 | 先用同步，保存参考结果 | 请求边界清楚，容易定位错误 |
| CPU 准备较重，GPU 工作期间 CPU 空闲 | 先用单路异步，准备下一帧 | 不增加 Context 就能尝试隐藏 CPU 时间 |
| 多路视频、离线批量、单请求未占满 GPU | 从 2 路开始，比较 1 / 2 / 4 路 | 找到吞吐、尾延迟与显存的合理点 |
| GPU 计算或显存带宽已饱和 | 保持少量路数，检查 batch 或计算优化 | 增加 Context 可能只增加竞争 |
| D2H 大、CPU 后处理慢 | 优先减少回传，考虑 Module 4 的设备内处理 | 多路不能消除多余传输与 CPU 瓶颈 |
| p95 上升，FPS 增长很小 | 降低路数、限制队列，定位队头阻塞 | 在途更多不等于完成更快 |
| 实时视频结果越来越旧 | 限定队列和结果年龄，按业务决定丢帧策略 | 平均 FPS 无法反映时效性 |

调路数时先固定输入、shape、精度与后处理，只改变 N。每次同时记录吞吐、mean / p95、显存与正确结果数；吞吐收益趋于平缓或尾延迟超过目标时停止加路。2 路、3 路都只是实验起点，没有通用最优路数。

在理想的独立复制 / 计算资源、足够多请求和足够缓冲条件下，流水线周期可能接近最慢阶段耗时；如果 H2D 与 D2H 共享瓶颈、计算已经饱和，或内部同步很多，这个近似就不成立。下一节 [3.4](3.4-serial-vs-parallel.md) 的重叠图和吞吐关系也应按这个理想条件理解，不能当成设备保证。

## 10. 常见错误速查

| 现象 | 优先检查 | 处理 |
|---|---|---|
| 一帧能跑，多帧随机错 | 在途 `h_in` / `d_in` 被覆盖，或输出尚未消费 | 每槽位独立资源，先 collect 再 submit |
| `ready()` 永远 false | 事件是否在正确 stream 记录，错误是否被吞掉 | 只把 `cudaErrorNotReady` 当作未完成 |
| 结果错位、尾帧丢失 | 仅按槽位号配对，或没有 drain | 校验 frame_id，按请求编号排空 |
| async 与 sync 一样快 | 无独立 CPU 工作、立即等待或 GPU 已饱和 | 看时间线与真实瓶颈，不只改函数名 |
| 多路反而更慢 / OOM | 内部执行内存增加，算力 / 带宽竞争 | 降低 N，测实际显存与尾延迟 |
| `enqueueV3` 失败 | I/O 容量 / 地址 / shape / profile 不完整 | 提交前校验，保留 TensorRT 日志 |
| enqueue 成功，回收报 CUDA 错误 | 前面异步 kernel / 插件 / 拷贝失败 | 检查同步返回值，定位最早错误 |
| 函数返回后旧结果变化 | 返回了被槽位复用的裸输出地址 | 复制到拥有存储的结果对象，或设计借用协议 |
| 程序退出时崩溃 | GPU 未完成就销毁 Context / Engine / buffer | 显式排空，异常路径也等待后清理 |
