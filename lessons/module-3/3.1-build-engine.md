# 3.1 从 ONNX 构建并缓存 TensorRT Engine

> **对应 SLT**：我能从 ONNX 构建并缓存 TensorRT Engine，并反序列化用于推理。
> **课时类型**：Developer Documentation
> **版本**：TensorRT 10.10.0.31（API 已核对）
> **前置**：1.1 环境、1.2 CMake 检测、2.2 预处理

本节重点不是“把一段代码抄下来”，而是理解一次 Engine 构建需要哪些步骤、每步依赖什么信息、TensorRT 在哪一步真正生成 Engine，以及构建后如何保存和验证。

---

## 先看完整流程

```text
准备 ONNX、TensorRT/GPU 环境和构建策略
        ↓
ILogger ──提供诊断信息──┐
        ↓                │
IBuilder ──创建──► INetworkDefinition
        │                       ▲
        │                       │ Parser 将 ONNX 解析并填入
        │                 nvonnxparser::IParser
        │
        ├──创建──► IBuilderConfig（精度、工作区、动态形状等）
        │                       │
        └──────── network + config
                                ↓
                  buildSerializedNetwork
                                ↓
                    序列化 Engine 字节
                                ↓
                    写入 .engine 缓存文件
                                ↓
IRuntime ──deserializeCudaEngine──► ICudaEngine
                                ↓
                     检查 I/O 张量信息
```

构建阶段（build phase）由 Builder 根据网络、配置和目标环境选择实现并生成序列化计划；运行阶段（runtime phase）再加载这个计划并执行推理。[TensorRT 工作原理](https://docs.nvidia.com/deeplearning/tensorrt/latest/architecture/how-trt-works.html)

要区分两件事：**构建 Engine**是 TensorRT 的工作；**检查缓存文件、决定复用还是重建**是应用程序的策略。本节用文件修改时间做一个教学用的简单缓存判断。

---

## 构建前：确认输入和目标

构建不是只由 ONNX 文件决定。至少要明确：

- **模型**：ONNX 文件及其输入输出、张量类型、算子和权重。
- **软件环境**：TensorRT 版本、CUDA/驱动及操作系统。
- **目标设备**：实际要运行 Engine 的 NVIDIA GPU。
- **构建策略**：是否允许 FP16、工作区上限，以及是否需要动态输入形状。

这些信息的来源不同：网络结构来自 ONNX；设备和软件版本来自构建机器；精度和资源限制来自应用的部署要求。TensorRT 默认不能保证一个 Engine 在任意版本、操作系统或 GPU 上都能使用；兼容性配置可以放宽部分限制，但需针对目标部署验证。[Engine Compatibility](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html)

---

## 代码开始前：认识 TensorRT 相关头文件

本节分步代码需要包含 TensorRT 核心 API 和 ONNX Parser 的头文件：

```cpp
#include <NvInfer.h>      // TensorRT 核心 API：ILogger、IBuilder、Network、Config、Runtime、Engine
#include <NvOnnxParser.h> // ONNX Parser API：nvonnxparser::IParser、createParser
```

`NvInfer.h` 提供 TensorRT 核心接口，包括 `ILogger`、`IBuilder`、`INetworkDefinition`、`IBuilderConfig`、`IRuntime` 和 `ICudaEngine`。其中 `IBuilder` 是 Engine 构建入口，`createInferBuilder()` 也由该头文件声明；它负责创建 Network 和 Builder Config，并调用构建接口生成序列化 Engine。`NvOnnxParser.h` 提供 `nvonnxparser::IParser` 和 `createParser()`，用于将 ONNX 模型解析并导入 TensorRT Network。头文件提供 API 声明，编译时还需链接对应的 TensorRT 库：核心库 `nvinfer` 和 ONNX Parser 库 `nvonnxparser`（见 1.2 的 CMake）。

## 第 1 步：创建 Logger 和 Builder

TensorRT 通过 `ILogger` 输出构建和运行时的错误、警告及信息。Builder 创建时需要 Logger，因此 Logger 是构建链的基础设施，不是模型本身的一部分。

```cpp
class Logger : public nvinfer1::ILogger
{
public:
    void log(Severity severity, const char* msg) noexcept override
    {
        if (severity <= Severity::kWARNING)
            std::cout << "[TRT] " << msg << "\n";
    }
};

Logger logger;
auto builder = std::unique_ptr<nvinfer1::IBuilder>(
    nvinfer1::createInferBuilder(logger));
if (!builder) throw std::runtime_error("创建 Builder 失败");
```

- `IBuilder` 是构建入口，也是创建网络和构建配置的工厂对象。
- Logger 的阈值决定哪些消息会显示。示例屏蔽普通信息，只显示警告和错误。
- 排查问题时可以提高日志详细度；Parser 自身的阈值也要相应提高，否则 Parser 可能不会产生详细消息。
- 检查 Builder 是否为空。创建失败时不能继续后续步骤。
- Logger 必须在使用它的 TensorRT 对象期间保持有效。

**来源**：`createInferBuilder(logger)` 是 TensorRT Builder API。日志消息由 TensorRT 在创建、解析、构建等阶段产生。

---

## 第 2 步：创建空的 Network Definition

```cpp
auto network = std::unique_ptr<nvinfer1::INetworkDefinition>(
    builder->createNetworkV2(0));
if (!network) throw std::runtime_error("创建 Network 失败");
```

`INetworkDefinition` 是 TensorRT 内部的网络表示。刚创建时它还没有模型层；下一步 Parser 会把 ONNX 的计算图解析进来。

TensorRT 10 中显式 batch 已默认启用，所以这里传 `0`，不需要再设置旧示例中的 `kEXPLICIT_BATCH` 标志。传 `0` 不表示关闭 batch。

**注意**：网络创建成功只说明拿到了空网络，不代表 ONNX 已经解析，也不代表 Engine 已构建。

---

## 第 3 步：创建 ONNX Parser 并解析模型

```cpp
auto parser = std::unique_ptr<nvonnxparser::IParser>(
    nvonnxparser::createParser(*network, logger));
if (!parser) throw std::runtime_error("创建 ONNX Parser 失败");

if (!parser->parseFromFile(
        onnx_path.c_str(),
        static_cast<int>(nvinfer1::ILogger::Severity::kWARNING)))
    throw std::runtime_error("解析 ONNX 失败: " + onnx_path);
```

Parser 把 ONNX 文件中的图、张量、权重和节点转换成 TensorRT 网络定义中的对象。数据来源是 ONNX；Parser 根据 TensorRT 的 ONNX 导入能力判断能否表达该网络。

解析失败不一定是文件不存在。也可能是 ONNX 中含有不受支持的算子或属性、导出形式不适配、张量类型不支持，或模型文件本身有问题。排错时应先看 Parser 日志指出的节点和算子，再针对该节点处理。

**这一阶段的产物是填充好的 `network`，不是 Engine。** Parser 负责导入，Builder 才负责后面的优化和构建。

---

## 第 4 步：创建并设置 Builder Config

```cpp
auto config = std::unique_ptr<nvinfer1::IBuilderConfig>(
    builder->createBuilderConfig());
if (!config) throw std::runtime_error("创建 BuilderConfig 失败");

config->setFlag(nvinfer1::BuilderFlag::kFP16);
config->setMemoryPoolLimit(
    nvinfer1::MemoryPoolType::kWORKSPACE, 1ULL << 30);
```

`IBuilderConfig` 描述 Builder 应遵守的构建选项。它与 network 一起传给构建调用。

### 精度选项：`kFP16`

`setFlag(kFP16)` 表示允许 TensorRT 在适用时使用 FP16 实现。它不表示 ONNX 一定要是 FP16，也不保证每一层都会用 FP16。具体选择取决于网络、GPU 和 TensorRT 可用的实现。

如果精度是产品要求，应把它当作需要验证的构建策略：确认目标 GPU 支持，检查构建日志，并使用代表性输入比较推理结果。不能仅凭“构建成功”判断精度满足要求。

### 工作区选项：`kWORKSPACE`

`1ULL << 30` 是 1 GiB（字节）。`setMemoryPoolLimit` 设置的是 TensorRT 构建时 `kWORKSPACE` 内存池的上限。它会影响可选择的层实现；限制太紧时，某些实现不能使用，严重时可能无法构建。

这**不是整个进程或 GPU 的总显存上限**。遇到构建资源问题应结合 TensorRT 日志、GPU 上其他任务和模型需求判断，不要假设“显存不足就一定要调小 workspace”。TensorRT API 文档说明，workspace 限制会影响可用的层实现。[C++ API：Building an Engine](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/c-api-docs.html)

### 动态形状模型的额外配置

如果模型输入含有运行时才确定的维度（动态 shape），通常还需在构建配置中创建并设置 optimization profile，声明输入维度的最小值、常用值和最大值。当前示例没有创建 profile，因此不能把它当作动态 shape Engine 的完整构建示例。运行时还需选择/设置 profile 和具体输入形状；下一节提到的 `setInputShape` 属于运行阶段的设置。

---

## 第 5 步：让 Builder 真正构建并序列化 Engine

```cpp
auto serialized = std::unique_ptr<nvinfer1::IHostMemory>(
    builder->buildSerializedNetwork(*network, *config));
if (!serialized) throw std::runtime_error("构建 engine 失败");
```

这是构建链中真正生成 Engine 的调用。Builder 使用已解析的 `network`、`config` 和目标构建环境，选择网络实现并生成序列化计划。官方 C++ API 将 `buildSerializedNetwork` 列为构建序列化 Engine 的接口。[C++ API：Building an Engine](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/c-api-docs.html)

返回的 `IHostMemory` 保存序列化后的字节。返回空指针表示构建失败，应结合 Logger 输出排查，而不是继续写缓存。

```cpp
const char* begin = static_cast<const char*>(serialized->data());
return std::vector<char>(begin, begin + serialized->size());
```

上面把 `IHostMemory` 中的数据复制进 `std::vector<char>`。函数返回时局部 `serialized` 会释放，但返回的 vector 仍拥有自己的副本。此时得到的是 Engine 数据，还没有写到磁盘。

---

## 第 6 步：保存 Engine 和判断缓存是否可复用

应用把序列化字节写到 `.engine` 文件；后续可直接读回，避免再次构建。示例将 `model.onnx` 对应的缓存命名为 `model.engine`，并比较修改时间：缓存存在且不早于 ONNX 时复用，否则重建。

```text
首次运行：读取 ONNX → 构建 → 写 model.engine
后续运行：读 model.engine → 跳过构建
```

这只是一个简化的缓存有效性规则。它能处理“ONNX 文件更新后比缓存新”的常见情况，但不能检测：

- TensorRT、CUDA/驱动或操作系统环境变化；
- GPU 更换；
- FP16、workspace、动态形状 profile 等构建配置变化；
- 文件内容变了但时间戳没有相应变化；
- 缓存文件写入不完整或损坏。

因此，部署用缓存还应记录/校验模型内容、TensorRT 版本、设备信息和构建配置，或在反序列化失败时删除并重建。兼容性取决于实际构建和运行条件，详见 NVIDIA 的[Engine Compatibility 文档](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html)。

本课的读写辅助函数用于展示二进制文件操作。实际代码还应检查 `tellg()`、`read()`、`write()` 是否成功，以及 `std::filesystem` 的错误码；否则可能把损坏或空文件误当作有效缓存。路径派生也要处理 ONNX 路径没有扩展名、或目录名本身含点号等情况。

---

## 第 7 步：反序列化并检查 I/O

```cpp
auto runtime = std::unique_ptr<nvinfer1::IRuntime>(
    nvinfer1::createInferRuntime(logger));
auto engine = std::unique_ptr<nvinfer1::ICudaEngine>(
    runtime->deserializeCudaEngine(engine_data.data(), engine_data.size()));
if (!engine) throw std::runtime_error("反序列化 engine 失败");
```

`IRuntime` 负责将序列化字节恢复成 `ICudaEngine`。这一步会暴露缓存损坏或运行环境不兼容等问题。只应反序列化自己构建的或来自可信渠道的 Engine；Engine 包含可执行内容，不能把它当作普通、无风险的数据文件。[TensorRT 工作原理：反序列化与信任边界](https://docs.nvidia.com/deeplearning/tensorrt/latest/architecture/how-trt-works.html)

接下来枚举张量：

```cpp
engine->getNbIOTensors();
engine->getIOTensorName(i);
engine->getTensorIOMode(name);
engine->getTensorShape(name);
```

这里检查输入输出的**名字、方向和构建时形状**。后续设置张量地址、分配缓冲区时要使用对应名称和形状。TensorRT 10 使用按名字访问的 I/O Tensor API；不要照搬旧版本基于 binding index 的示例。

若某个维度为 `-1`，通常说明这个维度是动态的，不代表解析失败。运行时还需要设置实际输入形状，并按实际形状分配缓冲区。

**反序列化成功只说明 Engine 被加载。** 本节尚未创建 `IExecutionContext`、分配输入输出缓冲区或执行推理，这些属于后续步骤。

## 把原代码按职责串起来

```cpp
std::vector<char> buildEngine(const std::string& onnx_path, Logger& logger)
{
    // 1. Builder：构建入口
    auto builder = std::unique_ptr<nvinfer1::IBuilder>(
        nvinfer1::createInferBuilder(logger));
    if (!builder) throw std::runtime_error("创建 Builder 失败");

    // 2. Network：TensorRT 内部网络；TRT 10 显式 batch 默认开启
    auto network = std::unique_ptr<nvinfer1::INetworkDefinition>(
        builder->createNetworkV2(0));
    if (!network) throw std::runtime_error("创建 Network 失败");

    // 3. Parser：把 ONNX 模型导入 Network
    auto parser = std::unique_ptr<nvonnxparser::IParser>(
        nvonnxparser::createParser(*network, logger));
    if (!parser) throw std::runtime_error("创建 ONNX Parser 失败");
    if (!parser->parseFromFile(onnx_path.c_str(),
            static_cast<int>(nvinfer1::ILogger::Severity::kWARNING)))
        throw std::runtime_error("解析 ONNX 失败: " + onnx_path);

    // 4. Config：描述精度和构建资源等策略
    auto config = std::unique_ptr<nvinfer1::IBuilderConfig>(
        builder->createBuilderConfig());
    if (!config) throw std::runtime_error("创建 BuilderConfig 失败");
    config->setFlag(nvinfer1::BuilderFlag::kFP16); // 允许适用的 FP16 实现
    config->setMemoryPoolLimit(
        nvinfer1::MemoryPoolType::kWORKSPACE, 1ULL << 30); // 1 GiB 上限

    // 动态 shape 网络还需要在此处配置 optimization profile。

    // 5. Builder 使用 Network + Config 生成序列化 Engine
    auto serialized = std::unique_ptr<nvinfer1::IHostMemory>(
        builder->buildSerializedNetwork(*network, *config));
    if (!serialized) throw std::runtime_error("构建 engine 失败");

    // 6. 复制序列化字节；调用方负责写入缓存文件
    const char* begin = static_cast<const char*>(serialized->data());
    return std::vector<char>(begin, begin + serialized->size());
}
```

对象顺序的要点：Parser 要先填好 Network；Config 要在 build 前准备好；最后由 Builder 把 Network 和 Config 一起交给 `buildSerializedNetwork`。序列化数据返回后，构建阶段对象不再参与后续推理；运行时用 `IRuntime` 和 `ICudaEngine` 加载它。

## 验证构建流程

编译时链接 `nvinfer` 与 `nvonnxparser`（见 1.2 的 CMake），然后运行：

```bash
./build-engine model.onnx
```

首次运行预期类似：

```text
从 ONNX 构建 engine（首次较慢）...
已写入缓存: model.engine
IO 张量 (2 个):
  images (输入) 形状 [1, 3, 640, 640]
  output0 (输出) 形状 [1, 84, 8400]
```

再次运行时，若缓存判断通过，应看到“复用缓存”。这验证了程序走了缓存分支；同时应核对 I/O 名称和形状是否符合模型预期。它还没有验证真实推理结果，推理验证在后续课程完成。

## 常见问题与处理思路

| 现象 | 可能原因 | 先检查什么 |
|---|---|---|
| Parser 报解析失败 | 算子、属性、类型或 ONNX 导出形式不受支持 | 打开 Parser 详细日志，定位具体节点和错误信息 |
| 创建 Builder 或 Network 失败 | 环境、库链接或对象创建失败 | 检查 TensorRT 安装、CMake 链接和日志 |
| `buildSerializedNetwork` 返回空 | 网络不支持、配置不合适或构建资源不足 | 查看构建日志；检查精度、workspace 和动态形状 profile |
| 构建显存压力大或失败 | 工作区需求、模型规模或其他任务共同影响 | 查看日志和 GPU 使用情况，再调整资源策略；workspace 不是总显存上限 |
| 反序列化返回空 | Engine 损坏或版本、设备、平台不兼容 | 确认缓存来源和环境；重建当前环境对应的 Engine |
| 形状含 `-1` | 存在动态维度 | 构建时设置 profile，运行时设置具体输入形状 |
| 第二次仍然重建 | 缓存不存在、路径不符或时间戳判断不通过 | 检查 ONNX/Engine 路径、读写错误和文件时间 |
| 复用缓存后加载失败 | 简单时间戳规则没有检查兼容性或文件完整性 | 扩充缓存元数据/校验，并在无效时重建 |
