# 3.4 串行与多路异步流水线：延迟还是吞吐

> **对应 SLT**：我能比较串行与多路异步流水线在延迟与吞吐上的差异。
> **课时类型**：Exploration
> **前置**：3.3 同步、异步与多路并行推理

---

## 两条曲线，两种取舍

推理系统的表现可以用两条曲线描述：

- **延迟（latency）**：一帧从进入系统到拿到结果要多久。
- **吞吐（throughput）**：单位时间能处理多少帧。

串行流水线和多路并行流水线，本质上是**在这两条曲线上选了不同的点**。串行把延迟压到最低，多路并行把吞吐推到最高。多数工程问题不是「哪个更好」，而是「我更需要哪一条」。

理解这个取舍，比记住某个配置更重要。

---

## 串行流水线

一次只处理一帧：上传、计算、回传、取走，然后处理下一帧。

```text
t0  帧A 上传 | 计算 | 回传 | 取走
t1                                   帧B 上传 | 计算 | 回传 | 取走
```

**特征**：
- 单帧延迟 ≈ 上传 + 计算 + 回传，没有排队。
- GPU 在传输段空闲，在计算段才有活。
- 显存占用最小，逻辑最简单，结果永远对齐。

**它擅长**：单目标实时跟踪、控制系统回环、每帧结果都要立刻用的场景。此时多等一帧都是负担。

---

## 多路并行流水线

同时让 N 帧在途，用 N 个 context 轮转提交。

```text
t0  帧A 上传 | 计算 | 回传
t0    帧B 上传 | 计算 | 回传
t0      帧C 上传 | 计算 | 回传
t1        帧D 上传 | 计算 | 回传   ← 帧A 的结果此时才被取走
```

**特征**：
- 上传、计算、回传在不同帧之间**重叠**，GPU 长时间保持忙碌。
- 吞吐趋近于 `1 / max(单段最慢的那一段)`，而不是 `1 / (三段之和)`。
- 单帧延迟变高：帧要排队，还可能等前面的帧先出结果。
- 显存占用约为 N 倍缓冲，代码复杂度上升。

**它擅长**：多路视频接入、离线批量推理、追求高 FPS 的服务。此时总吞吐比单帧快慢更值钱。

---

## 流水线的三个阶段

多路并行不是一启动就满速，它经历三个阶段：

1. **填充（fill）**：启动时前 N−1 帧还在途中，吞吐偏低。
2. **稳态（steady）**：N 帧同时在途，吞吐达到峰值。
3. **排空（drain）**：停止提交后，还要等最后 N−1 帧出来。

这解释了两个常见困惑：为什么并行模式**第一帧特别慢**，以及为什么**测速要把填充阶段排除**。做基准测试时先跑几十帧预热，再统计稳态值，否则会低估并行模式的吞吐。

---

## 对比表

| 维度 | 串行（单 stream） | 多路并行（N stream/context） |
|---|---|---|
| 吞吐 | 低，受段间间隙拖累 | 高，接近瓶颈段倒数 |
| 单帧延迟 | 低，无排队 | 略高，有排队 |
| GPU 利用率 | 低，间歇空闲 | 高，持续忙碌 |
| 显存占用 | 小 | ≈ N 倍缓冲 |
| 实现复杂度 | 低 | 高（buffer 隔离、保序、流同步） |
| 典型场景 | 实时单目标、控制回环 | 高 FPS 服务、多路视频、批量 |

---

## 什么时候选哪个

先问自己三个问题：

- **结果是「立刻要」还是「迟早要」？** 立刻要用（比如闭环控制）→ 串行；可以延后消费 → 并行。
- **瓶颈是延迟还是吞吐？** 延迟敏感 → 串行；吞吐敏感 → 并行，且路数 N 加到 GPU 计算饱和为止。
- **显存与复杂度能不能承受？** N 路并行意味着 N 份缓冲与更难的调试，嵌入式设备尤其要看显存余量。

一个常见的中间答案：**2 路并行**。它足以让上传与计算重叠，又不会把延迟推得太高，显存和复杂度也可控。

## 一些想请你思考的问题

- 你的项目里，一帧结果从产出到被使用，中间隔了多久？如果隔了几帧，串行省下的延迟其实有没有被用上？
- 如果 GPU 计算时间远大于传输时间，多路并行还能带来多大收益？瓶颈段是谁？
- 当 N 从 2 加到 4 再加到 8，吞吐会一直涨吗？什么时候开始不涨，为什么？
- 你的系统在「填充」和「排空」阶段会不会丢帧或错帧？保序逻辑覆盖到这两段了吗？
