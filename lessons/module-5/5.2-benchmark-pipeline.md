# 5.2 测量端到端延迟与吞吐：计时必须覆盖完成

> **对应 SLT**：我能测量端到端延迟与吞吐，对比 CPU、CUDA 与 TensorRT 配置。
> **课时类型**：How To Guide
> **前置**：3.3 请求回收、3.4 延迟/吞吐取舍、4.4 正确性、5.1 配置
> **资产**：[`5.2-summarize-benchmark.py`](../../assets/code-examples/5.2-summarize-benchmark.py)，仅依赖 Python 标准库。

## 一次 enqueue 不是一次完成

CPU 很快从 `enqueueV3` 返回，只能说明工作已经提交。若立刻停止计时，会把排队、GPU 计算和结果消费全部漏掉。

本节固定一个明确口径，按同一输入、模型契约、结果语义比较 A–E 路径。基准程序由 5.3 接入；本节先提供可以直接运行的统计工具和测量协议，不假定已有 `detector_speed_bench`。

## 步骤 1：区分三种时间

| 名称 | 开始 | 结束 | 包含什么 |
|---|---|---|---|
| `pipeline_e2e` | BGR 已准备好，尚未等待空闲 slot | 最终 CPU NMS 结果被消费 | 背压等待、CPU 预处理、传输、推理、解码与回收 |
| `video_e2e` | 读帧/采集之前或采集时间戳 | 业务使用结果 | 还含采集、解码及你明确选入的画框/编码等 |
| `gpu_span` | 同一 stream 上记录 begin event | D2H 完成后记录 end event | 两个 GPU 时间戳之间的间隔，可能包含 GPU 竞争/等待，不含全部 CPU 处理 |

主比较使用 `pipeline_e2e`，**不包含模型加载/engine 构建、视频读取、画框和写盘**。这些不是消失了，而是单独测冷启动、读写耗时或 video_e2e。

CPU timestamp 使用同一进程的 `std::chrono::steady_clock`，不要用会被校时调整的 wall clock，也不要把 CPU ns 与 CUDA event ms 相减。结果时间必须在同步完成、读到候选并执行 NMS 后记录。

## 步骤 2：先固定实验变量

在 5.1 的 A–E 配置基础上，记录：

- 相同 ONNX 内容 hash、输入帧序列、shape、padding/颜色/归一化规则、类别与阈值/NMS。
- 相同构建精度策略。TensorRT 的 FP32 路径也可能允许 TF32；若需要隔离算术差异，明确设置 builder 的 TF32 策略并记录。FP16 单列实验，不与「只改预处理」混在一起。
- CPU 线程数、GPU/驱动/CUDA/OpenCV/TensorRT 版本、device_id、slots、模型/engine hash。
- 运行 Release 构建；关闭 sanitizer、调试张量下载、逐帧日志和画框落盘；无其他重负载任务。
- 正确性报告先通过。跨后端原始输出不必逐位相等，但必须满足预先规定的模型结果容差；不是为某个更快结果临时放宽阈值。

将不同 BGR 帧提前读入内存，避免重复读盘混入 pipeline_e2e。记录这项选择；不要用同一帧循环作为唯一异步正确性测试。

## 步骤 3：预热、测量、排空

每次实验按同一协议执行：

1. 加载后端和模型，分配所有 slots。冷启动另记时间，不放进 FPS。
2. 用代表性输入预热，例如 30 帧；让每个 context/slot 都至少执行过一次。30 只是起点，若仍在发生懒初始化或时钟爬升，延长到稳定。
3. **完成并消费全部预热请求**，确认没有遗留输出，再开始 measured run。
4. 测量 N 帧，给 measured frame_id 编号 0..N−1。每帧 BGR 准备好后立即记录 ready，再等槽位；不要在等待结束后才记录 ready。
5. 记录 submit；提交请求，回收时同步对应完成 event，CPU NMS 后记录 done。
6. 提交完最后一帧后继续回收，直到 N 个结果都被消费；最后才结束计时。

本课程默认报告**有限批处理 FPS**：测量区间从最早 ready 到最晚 done，包含本批次的 fill/drain。增大 N 可以减弱边界影响，但不能漏掉尾帧。若另报「稳态 FPS」，须单列并说明稳态窗口和跨边界请求归属，不能与这里的口径混用。

离线测试不主动丢帧，slots 满时做背压。实时视频需要丢旧帧时，另记输入率、完成率、drop 数、queue 上限和 age-of-result；不能把少处理的帧算成更高吞吐。

## 步骤 4：记录 CPU 时间戳

下面是接到项目里的计时片段，不是完整 detector：

```cpp
#include <chrono>
#include <cstdint>
using Clock = std::chrono::steady_clock;
int64_t nowNs() {
    return std::chrono::duration_cast<std::chrono::nanoseconds>(
        Clock::now().time_since_epoch()).count();
}
// 帧到达/已准备好：frame.ready_ns = nowNs();
// 等待空闲 slot；旧结果必须先被消费。
// 在提交 CPU/GPU 工作之前：slot.submit_ns = nowNs();
// enqueue、event 完成、取回候选、CPU NMS。
// CPU NMS 后：result.done_ns = nowNs();
```

每个 slot 保留自己的 frame_id、ready、submit、几何参数与原图。CPU 后处理可能在另一个线程执行，仍使用同一 steady_clock；如果 NMS/消费有队列，其等待也计入 done−ready。

CSV 至少含四列，完成顺序可与提交顺序不同：

```text
frame_id,ready_ns,submit_ns,done_ns
```

只写**已完成且已消费**的请求。预热行不写入这个 CSV。禁止多个线程不加同步地同时写同一个流；先保存到内存，测量结束后统一写文件可减少扰动。

## 步骤 5：先用人工数据验证统计器

以下数字是**人工时间戳，不是 GPU 性能结果**。三个串行请求每个耗时 10 ms，总窗口 30 ms：

```bash
python3 - <<'PY'
from pathlib import Path
p = Path('/tmp/coach-bench-demo.csv')
p.write_text('frame_id,ready_ns,submit_ns,done_ns\n'
             '0,0,0,10000000\n'
             '1,10000000,10000000,20000000\n'
             '2,20000000,20000000,30000000\n')
print('WROTE', p)
PY
python3 assets/code-examples/5.2-summarize-benchmark.py \
  /tmp/coach-bench-demo.csv --expected-count 3 --label synthetic-serial \
  --json-out /tmp/coach-bench-demo.json
```

预期 `frames=3`、`FPS=100.000`，mean/p50/p95/p99 均为 10.000 ms；slot wait 为 0。脚本的 PASS 只说明计时数据合法，不说明推理正确或性能提高。退出码 2 表示缺列、重复/缺失 ID、时间倒序或非法数据。

统计约定：

```text
单帧 latency_i = (done_i − ready_i) / 1e6     [ms]
单帧 slot_wait_i = (submit_i − ready_i) / 1e6 [ms]
FPS = N / ((max(done) − min(ready)) / 1e9)
```

分位数采用排序后 `(N−1)*p` 位置的线性插值。尾延迟报告需要足够样本，三行示例并不能估计真实 p99。多路时，`1000/mean_latency_ms` 一般**不是 FPS**。

在项目输出真实 CSV 后，用同一命令替换输入路径、label 和 N；保存 JSON、原始 CSV、配置副本及环境信息，不只保留截图。

## 步骤 6：用 CUDA event 解释阶段，不替代端到端计时

需要定位 GPU 链路时，在 slot 的同一 stream 内记录 event：

```cpp
// begin/end 用 cudaEventCreate 创建，启用 timing；checkCuda 见 4.2。
checkCuda(cudaEventRecord(slot.begin, slot.stream));
// 入队 H2D、预处理、enqueueV3、解码、D2H；逐项检查返回值。
checkCuda(cudaEventRecord(slot.end, slot.stream));
// 回收这个 slot 时：
checkCuda(cudaEventSynchronize(slot.end));
float gpu_span_ms = 0;
checkCuda(cudaEventElapsedTime(&gpu_span_ms, slot.begin, slot.end));
```

完成 event 可另用 `cudaEventDisableTiming`，但用于耗时的 begin/end 不能禁用 timing。event 必须在读取计时前完成，读取后才能被下一请求重新 record。

- 多路的 GPU span 会重叠；把所有 slot 的时长相加再取倒数不是系统吞吐。
- 各阶段 event 的间隔含共享 GPU 调度/流内等待，不能无条件解释为独占 kernel 时间。
- `cudaDeviceSynchronize` 放在每个阶段会毁掉并行。正确性定位可以临时这么做，正式测速恢复到请求级 event 回收。
- 页锁定主机缓冲更适合异步传输；传输返回并不表示数据可读取或覆盖。

进一步需要真实重叠证据时，使用 Nsight Systems 看 H2D、kernel、D2H 与不同 stream 的时间线。**多个 stream 存在不代表一定重叠。** 工具安装好、5.3 程序完成后可采样：

```bash
nsys profile --trace=cuda,nvtx,osrt --output=/tmp/coach-pipeline \
  ./build/detector --config configs/deploy.yaml --input data/input.mp4 --bench
nsys stats /tmp/coach-pipeline.nsys-rep
```

应产生报告文件和统计表。profile 有开销，这次运行用于解释瓶颈，不与无工具的基准数据混合。

## 步骤 7：比较结果并做一次优化决策

每种配置至少运行 3 次，交错或随机顺序，避免始终让最后一个配置享受更热的设备。保留单次结果，报告中位数和波动，不把所有实验的帧简单拼起来隐藏差异。

| 配置 | slots | N/正确结果数 | mean/p50/p95/p99 ms | FPS | H2D/D2H 字节/帧 | 显存/波动 | 结论 |
|---|---:|---|---|---|---|---|---|
| A CPU DNN + CPU 前后处理 | 1 | 待测 | 待测 | 待测 | 待测 | 待测 | |
| B CUDA DNN + CPU 前后处理 | 1 | 待测 | 待测 | 待测 | 待测 | 待测 | |
| C TRT + CPU 前后处理 | 1 | 待测 | 待测 | 待测 | 待测 | 待测 | |
| D TRT + 融合/解码 | 1 | 待测 | 待测 | 待测 | 待测 | 待测 | |
| E D 的多路版本 | 2/4 | 待测 | 待测 | 待测 | 待测 | 待测 | |

H2D/D2H 字节从应用实际拷贝调用记账，说明是否含行 pitch；不能仅凭理论输出维度推断所有隐含传输。显存至少记录空载/模型初始化后/运行采样值；`nvidia-smi` 的设备总使用量可能含其他进程和遗漏瞬时峰值，不等于精确的本进程峰值。

后端微基准如 `trtexec` 有自己的输入准备、stream 与计时边界，可辅助判断 engine，但不包含本应用的 letterbox、CPU NMS 和排队，不能替代上述 FPS。

最后回答：瓶颈在哪里？只改了哪个变量？为什么选当前 slots？如果并行没有变快，可能是 GPU 已饱和或资源竞争；如果 CPU 更快，可能是模型太小或传输/同步开销大。**不要求 GPU 或并行必须赢。** 3.4 的重叠图是理想示意，只有相关硬件、内存和调度条件满足才有预期收益。

## 排错与验收

| 现象 | 优先排查 |
|---|---|
| enqueue 时间极短，实际结果很慢 | 是否计到完成/CPU NMS，是否漏了排队 |
| 并行 FPS 特别高但结果少 | 尾请求是否排空，expected-count 是否通过 |
| p95 很高 | slot 等待、CPU NMS、隐式同步、热降频/其他负载 |
| CUDA event 为零/无效 | event timing 是否启用、是否完成、是否提前复用 |
| 同一 CSV 多跑结果不同 | 先查文件是否被并发写或误混了不同实验 |

本节验收：提供正确性通过的 A–E 报告，或明确标记不可用配置及原因；解释计时边界、fill/drain、FPS 与单帧延迟的区别。不得用人工示例冒充实测数据。
