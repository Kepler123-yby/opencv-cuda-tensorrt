# 5.1 运行时配置：切换后端，不让 CUDA 开关含糊

> **对应 SLT**：我能通过 YAML 配置在运行时切换推理后端与 CUDA 开关。
> **课时类型**：How To Guide
> **前置**：1.2 后端检测、3.1 engine 缓存、4.3 设备驻留路径
> **资产**：[`5.1-deploy.yaml`](../../assets/configs/5.1-deploy.yaml)、[`5.1-validate-config.cpp`](../../assets/code-examples/5.1-validate-config.cpp)

## 这节解决什么

`cuda: true` 不能说明推理发生在哪里。它可能只启用了图像 resize，而模型仍在 CPU；也可能模型在 GPU，但预处理下载后又上传了一次。

把**推理后端、预处理、后处理和并发模式**分开配置。启动时输出实际路径，不允许悄悄换成另一个后端。这里的「运行时切换」指同一可执行文件读取不同配置后启动；**不包含有在途请求时热切换 context/engine**。

## 步骤 1：理解支持矩阵

本课程的最小工程支持下列组合。它们是项目约束，不是所有库的能力上限。

| 推理 backend | GPU 必需 | 预处理实现 | 后处理实现 | 模式 |
|---|---|---|---|---|
| `opencv_cpu` | 否；GPU 预处理时才需要 | `cpu` / `opencv_cuda` | `cpu` | `sync` |
| `opencv_cuda` | 是 | `cpu` / `opencv_cuda` | `cpu` | `sync` |
| `tensorrt` | 是，即使预处理在 CPU | `cpu` / `opencv_cuda` / `fused_cuda` | `cpu` / `cuda_decode` | `sync` / `async` / `parallel` |

- `cuda_enabled` 是**允许使用 GPU 功能**，不是「把所有环节搬到 GPU」。false 时，只允许 `opencv_cpu + cpu 预处理 + cpu 后处理`。
- `opencv_cuda` 推理是 OpenCV DNN CUDA backend，与 `cv::cuda::resize` 是两套能力；前者还需要 DNN CUDA/cuDNN 和模型算子支持。
- 本课程的 OpenCV DNN 路径输入是主机 blob、输出是主机 Mat。GPU resize 后仍可能 download；不要把它宣传为设备直连。
- `fused_cuda` 直接写 TensorRT 的设备输入，`cuda_decode` 直接读设备输出。此教学实现不把它们接到 OpenCV DNN。
- `precision: fp16` 仅开放给 TensorRT 构建。它不代表所有层、输入或输出都变成 half。当前 4.1/4.2 kernel 要求 FP32、LINEAR IO，不匹配时必须拒绝或另写转换。
- `parallel` 才启用多个 slot；`async` 是单 slot 异步提交，不保证吞吐提高。

## 步骤 2：从一份明确的 YAML 开始

课程根目录：

```bash
cd ~/courses-in-progress/opencv-cuda-tensorrt
python3 -c "from pathlib import Path; p=Path('assets/configs/5.1-deploy.yaml'); print(p.resolve(), 'exists=', p.is_file())"
```

应输出 `exists=True`。文件包含完整 schema；核心选择为：

```yaml
runtime:
  backend: tensorrt
  cuda_enabled: true
  device_id: 0
  precision: fp32
  mode: sync
  slots: 1
preprocess:
  implementation: fused_cuda
  pad_value: 124
postprocess:
  implementation: cuda_decode
  output_layout: candidate_major
  num_classes: 2
  score_threshold: 0.5
  nms_iou: 0.5
```

不要只复制这段去运行验证器：它省略了 schema、model、benchmark 字段。完整文件中的模型路径是**占位路径**，课程不附带模型或 engine。

| 字段 | 契约/检查 |
|---|---|
| `schema_version` | 当前为 1；不认识的版本、字段直接报错 |
| `model.onnx / engine` | 相对路径以 YAML 所在目录为基准；不能依赖启动时 cwd |
| `input_name / output_name` | 必须与模型/engine 中的真实名称一致 |
| `input_shape` | 此最小项目固定正数 `[1,3,H,W]`，batch=1；动态 engine 则先检查 profile 范围 |
| `device_id` | 指进程当前可见设备中的编号；`CUDA_VISIBLE_DEVICES` 会改变对应关系 |
| `precision` | 构建策略；实际 IO dtype 另从 engine 查询 |
| `mode / slots` | sync/async 为 1，parallel 为 2..8；8 是教学防误配置上限，不是硬件限制 |
| `pad_value` | 整数 0..255；124 仅用于本课程参考，不是通用默认值 |
| `output_layout / num_classes` | 对应 4.2 的无 objectness、已是类别分数的 xywh 输出；不适配 DFL/关键点/内置 NMS |
| `benchmark.warmup / frames` | 预热完成后再统计；必须成功回收 frames 个结果 |

配置文件与模型契约一起进版本控制，engine/cache、原始视频与大张量导出不必进源码仓库。

## 步骤 3：先验证 schema，再检查运行环境

验证器只依赖 yaml-cpp，不加载 CUDA、OpenCV 或 TensorRT。先确认开发包：

```bash
pkg-config --modversion yaml-cpp
```

应输出版本。本机是 0.7.0。缺少包时使用你系统的开发包或项目依赖管理方案，不要通过链接另一份 ABI 不匹配的库来凑齐。

编译、验证：

```bash
g++ -std=c++20 -Wall -Wextra \
  assets/code-examples/5.1-validate-config.cpp \
  $(pkg-config --cflags --libs yaml-cpp) -o /tmp/coach-validate-config
/tmp/coach-validate-config assets/configs/5.1-deploy.yaml
```

编译成功通常无输出，紧接着的验证应打印：

```text
PASS: schema and configuration relationships
backend=tensorrt cuda_enabled=true requires_gpu=true
preprocess=fused_cuda postprocess=cuda_decode mode=sync slots=1
...
NOT CHECKED: files, compiled capabilities, device, model IO, inference
```

退出码 0 是配置结构有效；2 是缺字段、拼错值或组合非法。**PASS 不等于模型能运行。** 在真正的 detector 启动路径里继续做以下检查，任何一步失败都停止启动：

1. 所选 backend 的代码和依赖是否编译进程序。CPU-only 构建可以合法运行 CPU 配置，不要求 TensorRT 或 OpenCV CUDA 都为 ON。
2. GPU 路径调用 `cudaGetDeviceCount`、检查 device_id，再 `cudaSetDevice`；使用 OpenCV CUDA 时也设置同一设备并检查其可用性。
3. DNN CUDA 路径查询 `cv::dnn::getAvailableTargets(cv::dnn::DNN_BACKEND_CUDA)`，检查所选 target；模型中不支持的层仍可能回退 CPU。检查启动日志及代表性模型的执行轨迹，不能只凭枚举判断全图在 GPU。
4. 按所选后端检查必要模型文件、engine manifest、输入/输出名称、resolved shape、dtype/format。不要对尚未解析的 `-1` 分配缓冲。
5. 使用正确输入跑一次初始化/冒烟请求，核对输出有限、shape 与语义；通过后才开始接收正式请求。

建议启动日志同时输出 `requested_backend` 与 `effective_backend`，以及 pre/post、device、精度策略、IO、slots、缓存命中原因。库内部的算子回退也应记录；不可把它误算成全 CUDA 实验。

## 步骤 4：做五组切换实验

复制完整 YAML 为不同实验配置，保留 model、阈值、几何契约不变，修改下表字段。这里的 C 是「TRT + CPU 前后处理」，D 才隔离融合路径的收益。

| 实验 | backend | CUDA 许可 | preprocess | postprocess | mode/slots |
|---|---|---|---|---|---|
| A | opencv_cpu | false | cpu | cpu | sync/1 |
| B | opencv_cuda | true | cpu | cpu | sync/1 |
| C | tensorrt | true | cpu | cpu | sync/1 |
| D | tensorrt | true | fused_cuda | cuda_decode | sync/1 |
| E | tensorrt | true | fused_cuda | cuda_decode | parallel/2，再试 4 |

先对每份配置运行 `/tmp/coach-validate-config PATH.yaml`。随后在 5.3 的工程中实例化对应路径。**目前附带的是配置验证工具，尚不是 detector 可执行文件。**

再做两个负向实验：

- 保留 `backend: tensorrt`，将 `cuda_enabled` 改成 false，应报 `GPU path requested while cuda_enabled=false`，退出 2。
- 将 `mode: parallel` 与 `slots: 1` 配对，应报 `mode/slots mismatch`，退出 2。

负向验证能防止配置静默失效，不需要实际推理即可运行。

## 步骤 5：部署 engine 与配置，而不是只复制 .engine

默认 engine 不应视为跨机器、跨 TensorRT 版本的可移植文件。兼容性标志可扩展部分适用范围，但不会自动使所有组合兼容；本项目先不启用它们。

缓存 manifest 至少记录：ONNX 内容 hash、TensorRT 10.10.0.31、GPU/计算能力、CUDA/插件环境、构建精度和 builder flags、输入 profile、IO 名称/shape/dtype/format。预处理、类别表、阈值与 NMS 规则记录在部署契约中。

缓存流程：先比对 manifest，再尝试反序列化；不匹配时有明确的「重建或报错」策略。构建失败不得覆写旧缓存，使用临时文件成功落盘后再原子替换。多个进程共享缓存时还需文件锁。线上可选择只加载已批准 engine，禁止临时构建。

只反序列化可信来源的 engine；不要把任意下载文件当成安全模型格式。验证部署包中的共享库路径，用受控 RPATH 或启动环境，避免加载到系统另一份 OpenCV/TensorRT：

```bash
# 在你完成并构建 5.3 的 detector 后运行：
ldd ./build/detector
```

应看到预期的 OpenCV、nvinfer、cudart 路径，无 `not found`。这是 ELF 依赖检查，不证明运行时延迟加载的插件均已找到，也不代替一次完整请求。

## 排错与验收

| 现象 | 优先排查 |
|---|---|
| 换了 YAML 但路径没变 | 配置是否实际被加载、是否被 CLI 覆盖、日志里 requested/effective 是否一致 |
| 能 resize，DNN CUDA 不可用 | DNN CUDA/cuDNN 与图像 CUDA 模块是不同能力 |
| TRT + CUDA=false 仍被运行 | 配置关系校验是否在工厂构造前执行 |
| 同名 engine 得到旧结果 | hash/精度/profile 是否进入缓存键和 manifest |
| 换工作目录后模型找不到 | 是否按 YAML 父目录解析相对路径 |
| CPU 配置却因 CUDA 库缺失无法启动 | 检查直接链接产生的进程依赖；运行时选择不能消除 ELF 启动依赖，必要时插件化或单独 CPU 构建 |

本节验收：合法配置输出预期路径，两个非法组合明确失败；解释「允许 CUDA」与「推理 backend」的区别。实际后端启动与不支持层的处理在综合项目里验收。
