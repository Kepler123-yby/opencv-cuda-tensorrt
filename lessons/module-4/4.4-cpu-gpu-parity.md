# 4.4 验证 CPU/GPU 一致性：先正确，再提速

> **对应 SLT**：我能验证 GPU 前后处理与 CPU 路径的结果一致性。
> **课时类型**：How To Guide
> **前置**：4.1 融合预处理、4.2 解码 kernel
> **本节资产**：`assets/code-examples/4.4-compare-tensors.py`（比较脚本，仅依赖 NumPy）和 `assets/code-examples/tests/verify-module4.py`（从课文提取 kernel 的独立测试，不加载 TensorRT engine）。

## 验证不只是「能画出框」

预处理错误可能只影响某种长宽比；原子压缩的顺序变化可能只影响分数相同的框；异步缓冲复用错误可能只在第几百帧出现。最终视频看起来正常，不能证明这些情况正确。

采用四层测试，失败时只排查对应层：

| 层级 | 固定输入 | 比较对象 | 主要定位 |
|---|---|---|---|
| 预处理 | 同一 BGR 图 | 同布局的 float NCHW | 颜色、step、采样、padding |
| 推理 | 同一 NCHW 张量、同一 engine | 同形状原始输出 | 地址绑定、生命周期、流依赖 |
| 解码 | 同一原始输出张量 | 按 ID 对齐的候选 | 布局、阈值、坐标逆变换 |
| 端到端 | 同一序列、匹配 frame_id | NMS 后结果与帧对齐 | 组合问题、异步错帧 |

不要一次同时换预处理、精度和 NMS，否则无法确定误差来源。

## 步骤 1：记录契约与测试环境

在课程根目录执行：

```bash
cd ~/courses-in-progress/opencv-cuda-tensorrt
python3 -c "import numpy as np; print('NumPy:', np.__version__)"
nvcc --version
nvidia-smi --query-gpu=name,driver_version --format=csv
```

均应产生版本输出。若 NumPy 不存在，在你的 Python 虚拟环境安装后重新检查，不修改系统 OpenCV 安装。

测试记录至少包含：TensorRT 10.10.0.31、OpenCV/CUDA 版本、GPU、模型与 engine 标识、输入输出 dtype/layout、padding 值、阈值、NMS 语义、并行路数。

## 步骤 2：分别导出 CPU 和 GPU 预处理张量

CPU 路径输出 RGB NCHW float32；GPU 路径按 4.1 输出同一布局。以下导出函数写原始 float32 字节，无头信息；本机 Linux 使用小端，脚本按小端读取。

```cpp
#include <fstream>
#include <stdexcept>
#include <string>

void writeFloatDump(const std::string& path, const float* values, size_t count)
{
    std::ofstream f(path, std::ios::binary | std::ios::trunc);
    if (!f) throw std::runtime_error("无法打开: " + path);
    f.write(reinterpret_cast<const char*>(values),
            static_cast<std::streamsize>(count * sizeof(float)));
    f.close();
    if (!f) throw std::runtime_error("写入失败: " + path);
}
```

GPU 下载仅用于检查，不放进正式设备驻留路径：

```cpp
#include <vector>

// kernel 已在 stream 上入队；checkCuda 定义见 4.2。
size_t elements = size_t(3) * target_w * target_h;
std::vector<float> gpu_dump(elements);
checkCuda(cudaMemcpyAsync(gpu_dump.data(), d_input, elements * sizeof(float),
                          cudaMemcpyDeviceToHost, stream));
checkCuda(cudaStreamSynchronize(stream)); // 同步后才能读取/写文件
writeFloatDump("gpu-pre.bin", gpu_dump.data(), elements);
// cpu_blob 为相同预处理契约下，连续的 RGB NCHW CV_32F blob。
writeFloatDump("cpu-pre.bin", cpu_blob.ptr<float>(), elements);
```

这些片段需要接到自己的 4.1 测试工程；课程没有假定你的仓库已经有某个 `cuda_parity_test` 程序。

输入 `[1,3,640,640]` 时，每个文件应为 **4,915,200 字节**：

```bash
wc -c cpu-pre.bin gpu-pre.bin
```

若长度不同，先查 shape、dtype、layout，不要通过调大误差阈值掩盖。

## 步骤 3：运行比较脚本

```bash
python3 assets/code-examples/4.4-compare-tensors.py \
  cpu-pre.bin gpu-pre.bin --shape 1 3 640 640 \
  --atol 0.007843137 --rtol 0
```

`0.007843137 ≈ 2/255` 是 uint8 CPU resize 与 float 融合采样的**初始测试阈值**。它不是通用正确性保证：若训练时要求严格复现特定插值与量化顺序，应采用那个实现作为基准，必要时修改 kernel。

脚本输出 shape、最大/平均误差、最大误差位置和不匹配数，并打印 `PASS` 或 `FAIL`。退出码：0 通过，1 数值不一致，2 文件/尺寸/NaN/Inf 等非法输入。

若使用相同浮点采样算法的 CPU 参考，可尝试更严格阈值（例如 `--atol 1e-5`），但正式阈值必须由测试与模型精度要求决定。

检查失败时的误差位置：整个 R/B 平面出错常是颜色顺序；斜纹常是 step；padding 边缘出错常是奇数补边；图像整体偏移常是采样坐标约定不同。

## 步骤 4：解码比较必须使用同一原始张量

先生成/保存一个原始输出张量，再分别交给 CPU 和 GPU 解码。不要把「CPU 预处理 → 推理」和「GPU 预处理 → 推理」的两个不同输出直接拿来判解码是否正确。

GPU 原子压缩顺序不稳定，按 `candidate_id` 对齐，依次核对：

1. 候选 ID 集合、类别完全一致。
2. 分数与坐标在规定容差内，所有数值有限。
3. NMS 用同一排序、同类抑制和 IoU 阈值规则。
4. score 恰好等于 threshold、分数相同的框都有明确处理。

对于 4.2 的人工 5 候选案例，要求 `decoded=4`、`nms_kept=3`，并打印保留的 ID，而不仅是数量。

若 engine 导出的是别的模型格式，先调整解码契约，再验证；不能用通用教学解码器去解释关键点、DFL 或带 NMS 插件的张量。

## 步骤 5：边界与异步测试

| 输入/操作 | 要暴露的问题 |
|---|---|
| 全黑、全白、RGB 各不相同的纯色 | 归一化、颜色顺序 |
| 梯度、棋盘格、随机图 | 插值和通道布局 |
| 641×480 → 640×640 的奇数 padding、横图、竖图 | 舍入、非对称 padding |
| 1×1 图、小 ROI、非连续主机图与带 pitch 的 GpuMat | 边界索引、step |
| 无候选、全部候选、capacity 不足 | count 清零、溢出处理 |
| NaN、负宽度、分数/IoU 恰等于阈值 | 数值与边界语义 |
| 1/2/4 路，输入逐帧不同 | 旧请求覆盖、错帧 |
| 连续提交后停止并排空所有请求 | fill/drain 漏结果 |

异步案例**不能一直使用同一张图**，否则错帧可能无法被发现。给帧保存 frame_id 与原图/几何参数，比较同一 ID 的结果；复用槽位前先完成旧请求并消费输出。实际场景的丢帧策略要单独测试。

课程附带一个不依赖模型/业务仓库的 smoke test，提取 4.1/4.2 的 kernel、编译并跑人工样本，再执行比较脚本的正常/异常测试。需要 nvcc、可用 CUDA GPU、CPU OpenCV Python、NumPy。下面算力参数用于本机 RTX 3060 Ti；其他显卡按 Toolkit 支持的算力修改：

```bash
python3 assets/code-examples/tests/verify-module4.py \
  --arch sm_86 \
  --opencv-include "$HOME/opt/opencv-cuda/include/opencv4" \
  --memcheck
```

`--opencv-include` 额外做 launcher 的编译检查；只有 kernel 测试时可省略。`--memcheck` 调用 compute-sanitizer，也可在工具未安装时省略。预期最后显示 `VERIFIED`，内存检查显示 `ERROR SUMMARY: 0 errors`。临时编译目录会打印出来，可查看生成代码、导出张量与 `metrics.json`。

这个测试验证预处理、人工解码和检查工具，不证明模型推理、全程并行或性能已通过。完整测试程序仍需接入真实 engine 和业务数据。

在调试构建中运行内存检查。下面的 `your_parity_program` 是你接入 4.1/4.2 后构建的测试可执行文件，不是课程已生成的二进制：

```bash
compute-sanitizer --tool memcheck ./your_parity_program
```

需要安装相应 CUDA 工具，并用 `-lineinfo` 构建来改善定位。验收是工具报告零内存错误，同时应用自己的比较测试通过。memcheck 不证明高层 frame_id 正确，也不证明所有跨流逻辑无竞争；仍需独立断言和压力测试。

## 步骤 6：正确性通过，再做性能 A/B

生产测速关闭调试下载、图像落盘、sanitizer 和逐帧日志。保持模型、输入、精度、阈值、NMS 与预热一致，分别测 CPU 基线和 GPU 驻留路径。

提交后必须等待所有在途请求完成，再停止端到端计时。记录至少：

```text
样本数 / 错帧数 / 最大误差
端到端 p50、p95 / FPS / 显存峰值
H2D、D2H 字节数 / 并行路数
```

性能没有提升仍可能是合理结论：输入很小、CPU 路径已经很快，或新的同步点超过了省下的传输。保留测量结果，不要求「GPU 必须赢」。

## 排错速查

| 现象 | 下一步 |
|---|---|
| 文件长度不同 | 检查 resolved shape、dtype、导出元素数 |
| 单帧正确，多路随机错 | 检查槽位复用、stream/event 和元数据生命周期 |
| 框数量一样但位置错 | 检查 cxcywh/xyxy、padding 与逆变换 |
| 只有 NMS 结果不同 | 检查排序 tie-break、class-aware 与 IoU 边界 |
| 刚好卡阈值的候选不同 | 固定同一原始张量再查数值与比较符号 |
