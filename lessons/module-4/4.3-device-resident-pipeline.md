# 4.3 「零拷贝」的工程含义：让中间数据留在 GPU

> **对应 SLT**：我能评估零拷贝设计如何消除 host↔device 往返。
> **课时类型**：Exploration
> **前置**：2.3 往返成本、3.3 异步推理、4.1–4.2 GPU 前后处理

## 先把术语分开

本课程前面用「零拷贝」描述减少中间结果的 host↔device 往返。严格地说，这里的主线是 **device-resident pipeline（设备驻留流水线）**：数据留在 GPU，各阶段直接复用设备缓冲。

CUDA 的另一种 zero-copy 是映射页锁定主机内存，让 GPU 访问 host 数据。在独立显卡上，它通常仍经过 PCIe，**不是免费访问，也不是显存带宽**。Jetson 的共享物理内存环境又不同，不能把 x86 独显的结论直接套用。

本节讨论的是第一种，目标是避免不必要的中间落地，而不是宣称整个系统完全没有拷贝。

## 三条数据路径

### A. CPU 前后处理

```text
CPU letterbox/blob
     ↓ H2D 模型输入
TensorRT
     ↓ D2H 完整输出
CPU decode/NMS
```

最容易调试。对小图、小模型、低候选数，它可能已经很快，应该保留为基准。

### B. 各阶段分别「用了 GPU」，但中间仍走 CPU

```text
原图 --H2D--> GPU resize/pad --D2H--> CPU blob
                                      ↓ H2D
                                  TensorRT
                                      ↓ D2H 完整输出
                               CPU 输出 --H2D--> GPU decode
                                                  ↓ D2H 候选
                                               CPU NMS
```

有 GPU 算子，不代表路径高效。多次上传下载加上 CPU 格式转换与等待，可能吃掉 kernel 的收益。

### C. 设备驻留

```text
原图 --一次 H2D--> GpuMat
                   ↓ fused preprocess
                 d_input
                   ↓ TensorRT
                 d_output
                   ↓ GPU decode/filter/compact
                 d_candidates
                   ↓ D2H count + 紧凑候选
                 CPU NMS/业务逻辑
```

仍然有第一次上传和最终结果回传，也仍有 GPU 对输入输出的读写。减少的是 B 路径中多余的中间落地。

| 优化位置 | 省掉的工作 | 仍需完成 |
|---|---|---|
| 融合预处理写 d_input | 下载补边图、CPU blob、再次上传模型输入 | 原图上传、采样与格式转换 |
| 后处理读 d_output | 完整输出 D2H 后再次 H2D | GPU 解码、候选回传 |
| 持久缓冲 | 逐帧 malloc/free 的分配成本与潜在同步 | 初始化分配、退出时释放 |
| 同流提交 | 阶段间 host 等待 | 正确的依赖顺序、最终消费等待 |

## 类型、布局和所有权必须相容

「把图像挂到 GPU」不是把指针强转后交给 TensorRT。检查三件事：

1. **类型与布局**：BGR uint8 HWC `GpuMat` 不等于 RGB float32 NCHW 模型输入。
2. **内存步长**：图像可能带 pitch；本例 TensorRT 输入要求连续线性平面。
3. **所有权与生命周期**：`setTensorAddress` 是绑定地址，不替你持有缓冲区，也不替你分配或释放应用 IO。

即便用 `GpuMat` 包装外部设备内存，包装只是视图，不意味着转换完成。写入、读取、释放的责任仍在调用方。先做正确的融合转换，再谈复用。

## 用一条 stream 建立顺序

最简单的正确基线：上传 → preprocess kernel → `enqueueV3` → decode kernel → 最终回传，都在同一条非默认 stream 上。

OpenCV 的 stream 和原生 CUDA stream 可以桥接：

```cpp
#include <opencv2/core/cuda_stream_accessor.hpp>

cv::cuda::Stream cv_stream = cv::cuda::StreamAccessor::wrapStream(stream);
gpu_image.upload(host_image, cv_stream);
// launchFusedPreprocess(..., stream)
// context->enqueueV3(stream)
// decodeKernel<<<..., ..., 0, stream>>>(...)
```

包装函数不替你管理请求完成状态。原生流、主机上传源、GpuMat、TensorRT IO 缓冲都要保持有效，直到对应任务完成。

不要在每个阶段后加 `cudaDeviceSynchronize()`。它会等待设备上的其他工作，把独立请求也拖入等待。调试期可以增加同步定位错误，正式路径应尽量只在消费点或必要的依赖处等待。

## 跨流时用 event，不用猜「应该已经好了」

把预处理与推理放到不同 stream 时，没有天然顺序，必须传递依赖。以下片段假设事件和流已初始化，生产代码检查所有返回值：

```cpp
// 预处理已经提交到 preprocess_stream
cudaEventRecord(preprocess_done, preprocess_stream);
cudaStreamWaitEvent(infer_stream, preprocess_done, 0);
// 现在 enqueueV3(infer_stream) 才可安全读取 d_input
```

`cudaStreamWaitEvent` 让设备侧排队等待，不需要 CPU 在两个阶段间阻塞。计时之外的完成事件可以用 `cudaEventDisableTiming` 创建。

event 只解决执行依赖，**不解决缓冲所有权**。如果其他请求此时覆写了同一个 `d_input`，即使 event 正确，结果仍会错。

## 多路并行：每个请求槽位持有自己的状态

一个槽位至少包含：

```text
execution context + stream + 完成 event
上传源 + GpuMat + d_input + d_output
d_count + d_candidates + host 候选缓冲
frame_id + 原图尺寸 + letterbox 参数
```

engine 权重可共享，但 context 的执行状态和并发请求 IO 不能随意共用。

槽位状态应是：

```text
IDLE → 已填入帧与元数据 → IN_FLIGHT → GPU_DONE → 结果已消费 → IDLE
```

提交第 k 帧到 `slot[k % N]` **之前**，检查旧请求完成，并保存/消费旧结果；否则新帧会覆盖旧帧的输入或输出。仅有一个 `% N` 取模，不构成安全流水线。

结果完成顺序可能与输入顺序不同。若业务需要保序，按 frame_id 重排；若业务允许取最新完成帧，显式记录丢帧策略与帧龄。框、关键点、原图和 letterbox 参数必须来自同一 frame_id，不能从「当前全局参数」还原旧结果。

## 收益不由「零拷贝」这个名字保证

GPU 驻留可能减少开销，但不能保证一定加速：

- 原图上传量可能比 CPU 缩放后的 NCHW float 输入更大，也可能更小，要按字节数算。
- 候选很少时，CPU decode 已很便宜；GPU kernel launch 和下载数量的等待可能成为新成本。
- 融合改变了量化/插值顺序，必须检查精度，不能只测 FPS。
- 多 stream 是并发机会，不是并发保证；是否真的重叠取决于 GPU 资源、传输条件和模型负载。
- 吞吐提升与单帧延迟不是同一指标；增加队列深度可能令控制系统拿到更旧的帧。

对 A/B/C 做相同输入、相同精度、相同阈值与 NMS 的 A/B 测试，记录：

```text
端到端 p50/p95 延迟、FPS、帧龄、显存峰值、每帧 H2D/D2H 字节数
```

CUDA event 可测同流 GPU 阶段，host 时钟测包含 CPU 工作和等待的端到端时间。只测 enqueue 的 host 调用时长，会把排队当作完成；省略 drain，又会漏掉最后在途的帧。

可以先回答几个具体问题：

- 当前路径哪一次 download 后，数据很快又被 upload？
- 最后 CPU 到底需要完整张量，还是少量候选？
- 若省了传输但多了两次等待，总延迟会变好还是变差？
- 队列变深后，控制逻辑读取的 frame_id 距离最新帧差几帧？
